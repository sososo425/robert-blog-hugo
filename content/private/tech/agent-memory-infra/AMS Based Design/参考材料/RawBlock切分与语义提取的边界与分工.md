好问题。这本质上是在问：**语义边界的确定权应该放在第4章（Block 生成时）还是第5章（抽取时）？**

参考材料的 Pipeline 设计实际上已经在 Step 5（切分粒度决策）做了语义分块——先按话题/意图切，再按 token 强制切。这跟现方案的 turn 级 Block + Window Scheduler 是两条路。

---

## 对比分析

| 维度           | **方案 A：现方案**（Ch4 turn 级 Block + Ch5 Window Scheduler） | **方案 B：语义分块前置**（Ch4 语义 chunk Block + Ch5 简化抽取） |
| ------------ | ----------------------------------------------------- | ---------------------------------------------- |
| **Block 粒度** | 1 turn = 1 block                                      | N turns = 1 block（按话题/意图边界切）                   |
| **Ch4 复杂度**  | 低（机械映射）                                               | **高**（需要语义判断：话题切换检测、意图变化检测）                    |
| **Ch5 复杂度**  | 高（Window Scheduler + 去重 + 合并）                         | **低**（每个 Block 已是语义完整单元，直接抽取）                  |
| **溯源精度**     | turn 级（最细）                                            | chunk 级（粗一档，但 chunk 内保留 turn_range 可回溯）        |
| **LLM 调用效率** | Window 拼接多 block → 一次调用                               | Block 本身就是合理上下文 → 一次调用                         |
| **指代消解**     | 依赖 Window 携带 context_blocks                           | **天然解决**——同话题 turns 已在同一 block 内               |
| **事件合并/拆分**  | 需要 Event Post-Processor 去重                            | **大幅减少**——语义完整的 chunk 天然对应完整事件                 |
| **滑动窗口去重**   | 需要（重叠区域产出重复事件）                                        | **不需要**——没有重叠                                  |

---

## 方案 B 的核心优势

**1. 消灭了 Window Scheduler 和 Event Post-Processor 两个复杂组件**

现方案最复杂的部分（滑动窗口、重叠去重、碎片合并）本质上都是在**弥补 turn 级 Block 的语义不完整性**。如果 Block 生成时就按语义切好，这些问题根本不会产生。

**2. "一发生一 event" 更容易实现**

语义 chunk 天然趋近于"一个话题/意图/任务"→ LLM 抽取时更容易输出正确粒度的 EventNode，不需要复杂的 prompt 指令（"多 block 合并"、"一 block 拆分"）。

**3. 参考材料的 Pipeline 与下游抽取更解耦**

Ch4 输出的 Block 已经是"自洽的语义单元"，Ch5 可以假设每个 Block 的上下文是完整的，prompt 更简单，模型表现更稳定。

---

## 方案 B 的核心劣势

**1. Ch4 需要引入语义判断，复杂度和成本前移**

参考材料 Step 5 的"语义判断"需要：
- 话题切换检测（embedding 相似度 / 小模型分类）
- 意图变化检测（规则 + 模型）
- 这些本身就需要模型调用或 embedding 计算

而现方案 Ch4 是**零模型依赖**（纯规则映射），所有智能都集中在 Ch5。方案 B 把模型依赖提前到了 Ch4，如果 Ch4 的语义切分出错，**错误会传播到整个下游**——一个被错误合并的 chunk 会导致事件信息混淆，且无法在 Ch5 挽救。

**2. 切分错误不可逆，turn 级 Block 更鲁棒**

| 错误类型 | 方案 A 的后果 | 方案 B 的后果 |
|---------|-------------|-------------|
| 该合并的没合并（切太细） | Window Scheduler 自动补偿 | 两个 Block 各自抽取 → 事件碎片化 → **无法挽回** |
| 该拆分的没拆分（切太粗） | 每个 turn 独立，无此问题 | 一个 Block 含多话题 → LLM 语义漂移 → **抽取质量下降** |

Turn 级 Block 是**无损的**——不做任何语义判断，所以不会引入错误。所有语义判断推迟到 Ch5，那里有 Window + LLM + Post-Processor 多层兜底。

**3. 增量处理变复杂**

参考材料也提到了增量场景（会话片段到达）。语义分块需要看到"足够多的上下文"才能判断话题是否切换，这意味着：
- 新 turn 到达时，可能需要**回溯修改已生成的 Block**（发现话题没切换，要合并回去）
- 或者需要等到 session 结束才能确定边界

Turn 级 Block 没有这个问题——每个 turn 到达即生成 Block，幂等、无回溯。

**4. 溯源粒度降低**

虽然 chunk 内保留 turn_range 可以回溯到 turn，但从 EventNode → source_block_id → Block → 具体 turn 多了一层间接寻址。现方案 EventNode.source_block_ids 直接指向 turn 级 Block，溯源更直接。

## 我的判断

**不建议改为方案 B，但可以吸收参考材料中的两个有价值的设计：**

### 值得吸收的

1. **Step 3 的清洗/压缩**：参考材料的噪声过滤 + 低密度压缩 与现方案 Ch5 的 Pre-Filter 功能重叠。可以把**纯规则的噪声过滤**（寒暄、空内容、system prompt）**前移到 Ch4**，让 Ch5 Pre-Filter 只做需要语义判断的分级（ENTITY_ONLY vs FULL）。这样 Ch4 过滤掉明显垃圾，Ch5 不用处理这些 Block。

2. **Step 4 的共指消解预处理**：现方案完全依赖 Ch5 Window 的 context_blocks 让 LLM 自行消解指代。但参考材料的规则层共指消解（"它" → 上一句唯一主语）成本极低，效果明显，可以加到 Ch4 作为可选步骤，降低 Ch5 的 LLM 负担。

### 不建议改的

**语义切分不要前移到 Ch4**。理由：
- turn 级 Block 是无损、幂等、零模型依赖的——这是系统最稳定的锚点
- 语义边界判断本质上是"理解"，放在有 LLM + 多层兜底的 Ch5 比放在 Ch4（一锤子买卖）更安全
- 参考材料自己也承认（Q1 结论）：如果下游用大模型，**可能不需要预切分**

> 一句话：**Ch4 做"确定性清洗"（过滤垃圾、消解简单指代），Ch5 做"语义判断"（窗口调度、事件边界）。把"不会出错的事"放 Ch4，把"可能出错的事"放 Ch5 多层兜底。**
