## 结论：应该容纳，但需要分清两件事

### 1. 程序性记忆是「二阶记忆」，不是直接抽取的

参考文档里明确写了：

> 程序性记忆不由单次情景直接写入，只由归纳映射（Memory Consolidation）在满足触发条件后生成。

这意味着它不像 EntityNode / EventNode 那样从 Raw Block 直接抽取，而是从**已有的情景记忆（EventNode）和语义记忆（EntityNode 关系）积累到一定程度后归纳产生的**。它的位置在 pipeline 中更靠后——是 SemanticCluster 同级甚至更下游的产物。

### 2. 来源不全是 Trace——分两类

你说的「程序性记忆应该主要来自 Trace」**对了一半**，具体要看 PM 的子类型：

| PM 子类 | 代表类型 | 主要来源 | 理由 |
|---------|---------|---------|------|
| **执行类** | PM-03 TaskExecution、PM-05 Fallback、PM-08 SOP-Workflow | **Trace 为主** | 你说得对——"用 async/await + error handling 解决并发问题成功率最高"必须来自真实执行记录，有 status=success/failure、有 latency、有工具调用链。Session 里聊再多方案，没执行过就不能固化为执行策略 |
| **交互类** | PM-01 Response Strategy、PM-02 Recommend、PM-04 Clarify、PM-06 User Rules | **Session 为主** | "回复编程问题时代码置顶"来自用户多次 Clarify/Feedback（EP-06/EP-08），这些信号只存在于 Session 对话中，Trace 里看不到用户对输出格式的满意度 |

所以更准确的说法是：**执行类 PM 的证据链必须锚定到 Trace 的 EventNode（tool_use / tool_result），交互类 PM 的证据链锚定到 Session 的 EventNode（user_request / decision / feedback）**。

### 3. 在现有图模型中如何容纳

我认为有两种思路：

**思路 A：新增 ProceduralNode（独立节点类型）**

```
ProceduralNode {
  pm_id, tenant_id, pm_type (PM-01~PM-08),
  trigger_condition,   // 触发条件
  strategy_desc,       // 策略描述（可执行的指令文本）
  confidence,          // 归纳置信度
  success_rate,        // 执行类 PM 特有：历史成功率
  evidence_count,      // 支撑的情景事件数量
  source_event_ids     // 归纳来源的 EventNode 列表
}
```

新增边：
- `DERIVED_FROM_PATTERN`: ProceduralNode → EventNode（归纳来源）
- `APPLIES_TO`: ProceduralNode → EntityNode（适用的实体/工具/场景）
- `SUPERSEDES`: ProceduralNode → ProceduralNode（策略演化，复用 superseded_at 机制）

**思路 B：作为特殊 SemanticCluster 的扩展**

不新增节点类型，而是给 SemanticCluster 增加 `cluster_type: "procedural"` 和策略相关字段。优点是模型不膨胀，缺点是 SemanticCluster 的职责会变模糊——它本来是「回顾性的事件聚合」，PM 是「前瞻性的行为指令」，语义上有本质差异。

**我倾向思路 A**，原因是：
- 程序性记忆是**规范性的（prescriptive）**——"Agent 应该怎么做"
- 情景/语义记忆是**描述性的（descriptive）**——"发生了什么 / 知道什么"
- 这两者的生命周期不同：PM 需要有 `success_rate` 持续更新，需要有 `SUPERSEDES` 做策略演化，这些在 SemanticCluster 上硬塞很别扭

### 4. 对当前方案的影响

如果容纳 PM，需要：

1. **图模型**（第 3 章）：新增第 5 类节点 ProceduralNode + 3 种边类型
2. **抽取 Pipeline**（第 5 章）：不受影响——PM 不在抽取阶段产生
3. **新增归纳模块**：概要设计的第 8 章（实体画像）或第 9 章（SemanticCluster）旁边，需要一个 **Memory Consolidation** 模块，负责从积累的情景事件中归纳产出 PM
4. **检索层**（第 10 章）：PM 需要参与检索——当用户发起新任务时，PPR 遍历应该能命中相关的执行策略
5. **遗忘机制**（第 11 章）：PM 的遗忘逻辑不同——success_rate 持续低的策略应该被淘汰

---

**核心判断**：程序性记忆值得纳入，但它不是第一阶段的必需项。建议先把情景+语义的 pipeline 跑通，PM 作为第二阶段扩展——因为 PM 依赖情景记忆的积累，没有足够的 EventNode 数据，归纳出来的 PM 也不可靠。
