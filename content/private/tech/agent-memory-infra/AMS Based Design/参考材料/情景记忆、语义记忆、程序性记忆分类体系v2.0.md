## 系统范围说明

|   |   |   |   |
|---|---|---|---|
|记忆类型|核心问题|持久化|本文覆盖|
|Episodic Memory（情景记忆）|发生了什么|✅|✅|
|Semantic Memory（语义记忆）|知道什么|✅|✅|
|Procedural Memory（程序性记忆）|Agent 应该怎么做|✅|✅|
|Working Memory（工作记忆）|当前对话上下文|❌ Session 内有效|❌ 由独立模块管理|

  

---

## 设计原则

|   |   |
|---|---|
|原则|说明|
|高覆盖|跨 10+ Agent 场景均可适用，无需重构分类|
|高抽象|按交互意图分类，而非按业务领域分类|
|有边界|每个类型有明确判定规则，避免抽取歧义|
|链路完整|情景归纳必须有明确目标类型承接，不允许信息丢失|
|可衰减|每条记忆携带元字段，支持置信度衰减与层级管理|

  

---

## 记忆通用 Schema（元字段）

所有三类记忆的每条记录均携带以下元字段：

```JSON
{
  "memory_id": "uuid",
  "memory_type": "episodic | semantic | procedural",
  "sub_type": "EP-01 | SM-02 | PM-03 | ...",
  "content": {},
  "importance_score": 0.85,
  "access_count": 3,
  "created_at": "ISO8601",
  "last_accessed_at": "ISO8601",
  "layer": "short | long",
  "source_session_id": "...",
  "confidence": 0.9
}
```

### 遗忘评分机制

记忆的可及性由综合分数决定，低于阈值的记忆不参与检索（先不物理删除，可被上下文线索重新激活）：

  

$$\text{Score}(m) = \alpha \cdot e^{-\lambda(t - t_{\text{last}})} + \beta \cdot f(\text{access\_count}) + \gamma \cdot \text{importance\_score} + \delta \cdot \text{confidence\_score}$$

  

- **第一项**：时间衰减（指数衰减），`short` 层 λ 更大，衰减更快
    
- **第二项**：访问频率强化，`f` 为饱和函数，防止高频记忆垄断检索结果
    
- **第三项**：初始重要性锚定，抽取时由 LLM 评分
    
- **第四项:** 置信度评分，抽取时由LLM评分
    

  

> **工程考虑**：设计异步 Memory Maintenance Job 定期重算 Score 并做 short→long 层级迁移，而非在检索时实时计算。少量高质量记忆优于大量低质量积累。

  

  

## 一、情景记忆（Episodic Memory）

> 回答"**发生了什么**"。每条记录绑定具体事件，有时间戳、有原始上下文。 前 17 种来源于 Session（对话层），后 3 种来源于 Trace（执行层）。 情景记忆是原始事件日志，本身不做归纳，归纳产物写入语义记忆或程序性记忆。

## 二、语义记忆（Semantic Memory）

> 回答"**关于这个用户/世界，我知道什么**"。 无时间戳，是经过归纳的抽象知识，不绑定任何具体事件。 语义记忆仅描述用户特征和世界事实，不描述 Agent 自身行为规范（行为规范在程序性记忆）。 分四层：用户画像层 → 实体知识层 → 关系事实层 → 聚合知识层。

---

## 三、程序性记忆分类（Procedural Memory）

> 程序性记忆回答"**Agent 应该怎么做**"。 与情景记忆的区别：情景记忆是"某次具体发生了什么"（有时间戳、有原始上下文）； 程序性记忆是"从多次情景中归纳出的可执行行为规范"（无时间戳、是抽象策略）。
> 
> 与语义记忆的区别：语义记忆描述"关于用户/世界的知识"（知道什么）； 程序性记忆描述"Agent 自身的行为准则"（怎么行动）。
> 
> **写入方式**：程序性记忆不由单次情景直接写入，只由归纳映射（Memory Consolidation） 在满足触发条件后生成。

### 3.2 PM 与 SM 的关键边界

这是最容易混淆的地方，逐一说清楚：

|   |   |   |   |
|---|---|---|---|
|容易混淆的对|SM 侧（用户知识）|PM 侧（Agent 行为规范）|判定规则|
|SM-02 Preference vs PM-01 Strategy-Response|"用户喜欢先看代码再看解释"|"回复编程问题时，代码块置顶，解释后置"|SM 描述用户特征；PM 描述 Agent 的行动方式|

|SM-07 Insight-Rule vs PM-07 Rule-SystemPolicy|"已知该用户的退款政策是30天"|"处理退款请求时，优先确认下单日期再给结论"|SM 是关于世界/用户的知识；PM 是 Agent 处理该知识的操作规程|
|SM-06 Insight-Pattern vs PM-03 Strategy-TaskExecution|"用户经常在周五下午提数据分析需求"|"数据分析任务优先给 SQL + 可视化，不只给文字结论"|SM 描述用户行为规律；PM 描述 Agent 执行任务的方式偏好|

## 四、情景→语义/程序性 归纳映射规则

> 这是三类记忆系统的核心枢纽，定义了情景记忆在什么条件下归纳产生语义记忆或程序性记忆。 v2.0 关键修复：补全了原 v1.0 中断裂的归纳链路，所有情景类型现在都有明确的目标承接。

### 4.1 完整归纳映射表

|   |   |   |   |
|---|---|---|---|
|触发情景类型|触发条件|归纳产出目标（SM/PM）|归纳逻辑|
|EP-07 Reject × N≥2，同类对象|同一用户，同类被拒对象≥2 次|SM-02 Preference / SM-03 Constraint|提取 rejected_item 的公共属性，写入偏好或约束|
|EP-06 Clarify × N≥2，同类纠正|同一纠正方向重复出现|SM-02 Preference + PM-01 Strategy-Response|SM 侧记录用户偏好；PM 侧同步更新 Agent 的回复格式规则 ← v2.0 修复断裂点|
|EP-08 Feedback（负向） × N≥2|同类输出反复获得负反馈|SM-02 Preference + PM-01 Strategy-Response|SM 侧记录用户不满偏好；PM 侧更新 Agent 回复策略 ← v2.0 修复断裂点|
|EP-05 Recommend + user_reaction=accept × N≥3|同类推荐持续被接受|SM-02 Preference + PM-02 Strategy-Recommend|SM 侧记录偏好；PM 侧更新推荐策略的 accept_pattern ← v2.0 修复断裂点|
|EP-05 Recommend + user_reaction=reject × N≥2|同类推荐持续被拒绝|SM-03 Constraint + PM-02 Strategy-Recommend|SM 侧记录约束；PM 侧更新 reject_pattern + 降低该类推荐优先级 ← v2.0 修复断裂点|
|EP-01 Task + status=success × N≥3，同类型|同类任务多次成功，方式一致|SM-06 Insight-Pattern + PM-03 Strategy-TaskExecution|SM 侧记录行为模式；PM 侧归纳最优执行方式 ← v2.0 修复断裂点|
|EP-01 Task + status=failure × N≥2，同类型|同类任务反复失败|SM-06 Insight-Pattern + PM-05 Strategy-Fallback|SM 侧记录失败模式；PM 侧更新兜底策略|
|EP-14 Negotiation + 达成明确约定|单次协商即可触发|PM-06 Rule-UserDefined（直接写入，无需多次）|用户明确协商的规则优先级最高，立即固化为 PM|
|EP-11 Constraint（hard 类型）|单次声明即可触发|SM-03 Constraint + PM-06 Rule-UserDefined|Hard 约束同时写入 SM（事实层）和 PM（行为规则层）|
|EP-12 Goal × N≥2，同方向|同一目标方向多次出现|SM-05 Attribute-Goal|归纳用户中长期目标，更新 horizon 和 confidence|
|EP-13 Learning，同主题积累|同主题学习事件≥3 次|SM-01 Attribute-Skill（用户技能提升）|更新 level 字段（beginner → intermediate → expert）|
|EP-02 QA，同领域高频|同领域问题≥5 次|SM-15 Fact-Domain|提取领域通用知识，与用户个人无关|
|EP-09 Emotion，同触发重复|同类触发导致情绪≥3 次|SM-06 Insight-Pattern|记录情绪触发模式，供 PM-04 澄清策略使用|
|EP-03 Problem + resolution 成功 × N≥2|同类问题用同种方式解决≥2 次|PM-08 SOP-Workflow|归纳问题解决的标准流程|

### 4.2 归纳映射关键说明

**双写规则**（SM + PM 同时写入的场景）：

- EP-06 Clarify：SM 记录"用户偏好什么"，PM 记录"Agent 应该怎么回复"
    
- EP-11 Constraint (hard)：SM 记录"约束事实"，PM 记录"如何执行该约束"
    
- EP-14 Negotiation：SM 可选记录用户特征，PM 必须记录约定规则
    

**单次触发** **vs** **多次积累**：

- 单次触发：EP-14 Negotiation、EP-11 Constraint (hard) → 用户明确表达，立即固化
    
- 多次积累：EP-06/EP-07/EP-08/EP-05/EP-01 → 需要观察稳定模式后才归纳
    

**触发阈值建议**（可根据场景调整）：

- 强信号（hard constraint、明确拒绝）：N≥2
    
- 弱信号（偏好、模式）：N≥3
    
- 领域知识：N≥5

## 五、类型判定边界与混淆处理

> 给出 8 组容易混淆的类型对及区分规则，确保 LLM 抽取时分类准确。

|   |   |   |   |
|---|---|---|---|
|混淆对|类型 A|类型 B|区分规则|
|EP-06 Clarify vs EP-07 Reject|用户纠正理解或输出方式|用户明确拒绝具体建议|Clarify：指出错误但愿意继续；Reject：不接受该方案，要求换方案|
|EP-03 Problem vs EP-04 Failure|障碍尚未解决，任务继续|任务已终止且无 Solution|Problem：报了错但继续尝试；Failure：放弃任务或 Agent 无法解决|
|EP-09 Exploration vs EP-10 Decision|无最终选择，在探索阶段|有明确选择|"看看有哪些方案" = Exploration；"用这个" = Decision|
|EP-11 Constraint vs EP-07 Reject|主动声明限制（未触发具体方案）|针对已有方案否定|"我不能跑步" = Constraint；"不要推荐慢跑" = Reject|
|SM-02 Preference vs SM-03 Constraint|倾向性，可违反但不喜欢|不可突破，违反会导致问题|"偏好国产品牌" = Preference；"不能使用未审批依赖" = Constraint|
|SM-06 Pattern vs SM-07 Rule|归纳出的行为规律，用户未必明说|可追溯到用户显式或确认的规则|"用户总是先试自己的方法" = Pattern；"周五不排会" = Rule|
|SM-07 Rule vs SM-16 Domain Fact|针对这个用户的行为准则|领域通用知识，与用户无关|"这个用户必须先测试再上线" = Rule；"Python的GIL限制并发" = Domain Fact|
|SM-17 Cluster vs SM-08 Goal|已发生事件的主题聚合（回顾性）|用户未来意图（前向性）|"3月处理了多次asyncio问题" = Cluster；"要把项目迁移异步" = Goal|
