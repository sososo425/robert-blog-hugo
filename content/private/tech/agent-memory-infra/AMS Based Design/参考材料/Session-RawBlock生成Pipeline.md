1. 会话装配与去重
    
      **目标：**解决会话不连续或者重复消费问题
    
    2. 装配：会话片段分批或者乱序到达
        
    3. 去重：消息重复消费问题
        
2. 格式标准化
    

**目标**：消除上游异构字段，得到内部统一的

|   |   |   |
|---|---|---|
|**字段**|**类型**|**说明**|
|session_id|str|必填|
|turn_index|int|会话内单调递增|
|role|enum|user / assistant / system / tool（后两类多进过滤）|
|content|str|纯文本或经 Markdown 规整|
|timestamp|datetime|缺省可用「上一 turn 时间 + ε」或入库时间，并打标 time_inferred|

3. 清洗与压缩
    
      **目标：**减少噪声与无效 API 调用；被过滤的 turn **不生成 RawBlock**
    
      【噪声过滤】
    
    > 噪声过滤规则应 **可配置**，避免把短但信息密度高的用户指令误删
    
    |   |   |   |
    |---|---|---|
    |**类别**|**典型特征**|**默认策略**|
    |System prompt|role=system 或固定前缀|丢弃或单独存档，不进抽取链|
    |纯寒暄|短句 + 高频词表（「好的」「谢谢」「哈哈」）|丢弃或合并入相邻块（谨慎：合并会改变块边界）|
    |工具调用|role=tool 或 JSON tool 块|默认丢弃；可选「摘要一行」挂到 assistant turn 的附录|
    |空内容|content 空白|丢弃|
    
      【低密度压缩】--（可选）
    
    > 当 会话turn的content很长但信息密度低时，用摘要替换原文，节省存储，也提升后续记忆抽取的信息密度
    
      典型场景：
    
    8. AI 长篇列举：“根据您的问题，以下是完整的 15 条解决方案：第一，检查网络连接……（重复类似句式 15 次）……第十五，重启设备。以上就是全部建议。”
        
    9. AI 冗余客套：“很高兴您问这个问题，这是一个非常好的问题。让我来详细解答一下……（3000 字后）……希望这个回答对您有帮助，如果还有问题请随时问我。”
        
    10. AI 重复用户问题：“您问的是‘如何配置 Kafka 消费者组’，关于‘如何配置 Kafka 消费者组’这个问题，我的理解是您想了解……（正文）”
        
    
      **是否需要判断****标准**
    
    |   |   |
    |---|---|
    |条件|建议|
    |下游 LLM 上下文窗口极小（如 4K）|✅ 强烈建议|
    |会话中经常有超长 AI 回复（>2000 字）|✅ 建议|
    |主要处理短问答（<500 字）|❌ 不需要|
    |下游模型支持长上下文（如 128K）且成本不敏感|❌ 可跳过|
    |需要保留完整回复供人工审计|⚠️ 保留原文 + 可选压缩|
    
4. 共指消解预处理（可选）
    

> 也可以在记忆提取缓解去做，这里做作用是 **减轻** **LLM** **负担、提高结构化输出稳定性**

**目标**：降低三元组抽取阶段「悬空代词」比例；**不追求完整指代消解**，只做高性价比预处理

  **推荐分层**：

1. **规则层**：人称代词（他/她/它/这个库）→ 若上一句唯一主语明确则替换；否则加括号标注候选（如 `pandas（候选）`）或保留原词。
    
2. **小模型层（可选）**：仅对含代词且规则未解决的句子调用轻量模型，输出「替换后文本」或「候选列表」；写入 `content_resolved` 字段供抽取使用，**保留** **`content_raw`** **利于溯源**（若存储空间允许）
    

3. 切分粒度决策
    
    > 遵守尽量保留完整session的大原则
    
    2. 首先按照session的token作为切分的基线
        
    3. 如果需要切割，再按照 **话题边界、时间间隔、强制切分策略**
        
4. Block 生成与存储
    
    1. Block数据模型设计以及物理存储引擎选择
        
    2. Block生成后直接进入phrase2（实体抽取）串行执行，也可以消息方式异步解耦

#### BlockContent

```TypeScript
Class BlockContent {
     block_id: string              // 关联 metadata
     session_id: string
      // 原始 Turn 列表（经过清洗、可选压缩）
     turns: Turn[]
      // 可选：压缩标记与原文指针
     is_compressed: boolean        // 是否经过低密度压缩
     original_uri?: string         // 若压缩，原始未压缩内容的存储位置
 }
```

#### Turn

```TypeScript
 class Turn {
     turn_index: number
     role: "user" | "assistant"
     content: string               // 经过标准化、可选清洗后的正文
     timestamp: string
     content_raw?: string          // 清洗前原文（可选，用于调试）
     is_filtered?: boolean         // 是否被过滤（若过滤则 content 为空）
     filtered_reason?: string
 }
```

### 存储设计

> 测试验证可以使用嵌入数据库（SqlLite/LanceDB）

**方案一、元数据+数据分离**

1. 基于PostgreSQL 直接存储轻量元数据
    
2. 对象存储（S3 / OSS）存储 BlockContent 完整 JSON
    

**方案二、数据湖统一存储（Iceberg/paimon）**

Block元数据和内容统一schema：底层存储适用Parquet + 对象存储

  

**【对比】**

|   |   |   |
|---|---|---|
|维度|方案一（PG + 对象存储）|方案二（数据湖）|
|适用规模|百万级 Block|亿级 Block|
|点查延迟|低（~10ms，加缓存更优）|中（~50-200ms）|
|分析查询|需导出或同步|原生支持（SQL on Lake）|
|运维复杂度|低|中高|
|一致性保证|需应用层处理|原生 ACID|
|存储成本|低|低（Parquet 压缩更好）|
|下游入图|需要先读取 S3 内容|可直接查询|

  

# 核心问题

## Q1: 如何chunk Session？chunk粒度是什么

**[核心原则]**

1. **语义****一致性****优先：单一语义/主题优先**可缓解记忆抽取时LLM语义漂移与Attention稀释
    
2. **语义完整性优先**：在 Session 长度允许的前提下，尽量保留全部对话为一个 Block
    
3. **完整性优于长度控制（但有边界）**
    
4. **溯源能力**：Block 保留原始对话内容，支撑后续记忆回溯
    

**【不同场景下结论】**

> 使用LLM在 “完整性优先 > 语义纯度”的选择博弈，LLM在多Topic/intent混合场景下：
> 
> 1. Attention 稀释
>     
> 2. 语义干扰（semantic interference）
>     

|   |   |   |
|---|---|---|
|**场景**|**是否需要 Phase 1 语义切分**|**原因**|
|**Phase 2 用大模型（****GPT-4****/Llama 3）**|1. **多情景/多主题/多任务 -> ✅ 可能需要**<br>    <br>2. ❌ 可能不**需要**|1. LLM语义漂移<br>    <br>2. LLM本身能理解主题边界|
|**Phase 2 用大模型（****GPT-4****/Llama 3）**|❌ 可能不需要|LLM本身能理解主题边界|
|**Phase 2 用小模型（****BERT****）**|✅ 可能需要|小模型需要预处理辅助|
|**需要实时流式处理**|✅ 可能需要|不能等整个session结束|
|**Session极长（>10k tokens）**|✅ 可能需要|超过LLM上下文限制|
|**成本敏感（想减少LLM调用）**|⚠️ 可选|但embedding也有成本|

## Q2:Session会话形态怎样？

> Session会话是从短期记忆promotion为长期记忆时触发，session内容与格式依赖短期记忆
> 
> 不要求上游一次性给满「整段会话」；但每条消息应尽量携带 **`session_id`** **+** **`turn_index`** **+** **`timestamp`****+Role+****msg**

1. 目前主要接收是完整session或者session的片段，基本理解是多round的批粒度
    
2. 预处理模块接受的逻辑输入是 **一组有序消息**，在业务上对应「一轮或多轮」对话，且可能是：
    

|   |   |   |
|---|---|---|
|**形态**|**说明**||
|**完整 Session**|从会话开始到结束的全量 turns，带稳定 session_id||
|**部分 Session / 切片**|仅包含 [turn_i … turn_j]，用于增量入库、重放、或失败重试||
|**单轮**|仅 1 个 user turn（可无 assistant 回复，或异步稍后补全）||
|**多 Session 批量**|多条会话并行处理；预处理按 session_id 分组，块内顺序仍按 turn_index|待确认|

## Q3:Session 中不同角色的content的处理

**根本原则**：记忆是关于“用户”的，不是关于“世界”的。Assistant 生成的事实性知识不应存入用户记忆

**【核心原则】**

|   |   |   |   |   |
|---|---|---|---|---|
|角色|核心价值|处理优先级|主要用途|进一步说明|
|User|高|⭐⭐⭐|记忆抽取、画像构建、意图识别|特殊场景<br><br>1. 用户对 Assistant 反馈 =》提取反馈意图，不提取 Assistant 内容<br>    <br>2. 用户提问含指代=》需要 Assistant 内容辅助理解，但不提取<br>    <br>3. 用户长篇提问=》可做摘要，保留核心意图|
|Assistant|中低|⭐|上下文理解、指代消解、交互状态追踪|高效处理策略<br><br>1. 语义锚点：Assistant 仅作为理解用户问题的背景，不存储=》科普、教育、通用对话<br>    <br>2. 动态丢弃：处理完即丢弃，只保留 User 序列=》纯 Q&A、客服、检索<br>    <br>3. 差异提取：只记录用户因 Assistant 产生的状态变化=》深度个性化、学习伴侣|
|System|低|⭐|会话元信息、流程控制||

**【针对信息密度低的Assitant内容的压缩处理】**

|   |   |   |   |   |   |
|---|---|---|---|---|---|
|方案|技术|速度|压缩比|信息保留度|实现复杂度|
|A. 提取式摘要|BERT Extractive Summarizer|⚡⚡⚡ 极快|5-10x|中|低|
|B. 生成式摘要|BART (fine-tuned)|⚡⚡ 快|10-20x|高|中|
|C. 纯关键词提取|RAKE/TF-IDF/TextRank|⚡⚡⚡ 极快|20-50x|低-中|极低|
|**D. 混合方案**|**关键词 + BART 摘要**|**⚡⚡ 快**|**15-25x**|**高**|**中**|

**【压缩处理的判断】**

|          |                  |                 |     |
| -------- | ---------------- | --------------- | --- |
| 维度       | 判断标准             | 说明              | 具体  |
| 长度       | 超过 150-200 字符    | 短回答直接保留原文，无需压缩  |     |
| 信息密度     | 事实性知识 vs 社交性回复   | 科普回答密度高，闲聊回复密度低 | 主要  |
| 对记忆提取的价值 | 是否影响下轮 User 意图理解 | 高价值才需要保留摘要      |     |
| 内容类型     | 解释/说明 vs 确认/问候   | 解释型需要压缩，确认型可丢弃  |     |
