## 一、EntityNode 抽取粒度：不是"全部都要抽"，而是"按记忆功能分层过滤"

你的直觉是对的：**"巴黎是法国的首都"这种客观事实不需要进图谱。**

但关键区别不是"客观 vs 主观"，而是你说的——**是否带有情景锚定（situational grounding）**。我把这个逻辑更精确地展开：

### 三层过滤模型

| 层级            | 类型              | 例子                                      | 是否抽取                       | 理由                              |
| ------------- | --------------- | --------------------------------------- | -------------------------- | ------------------------------- |
| **L0：通用常识**   | LLM 天然知道的事实     | 巴黎是法国首都、Python 是编程语言                    | ❌ 不抽                       | 白噪声，只增加图谱体积，检索时不会被查到            |
| **L1：领域静态知识** | 行业/领域内的稳定事实     | "我们公司用 Kafka 2.8"、"数据仓库分层是 ODS→DWD→DWS" | ⚠️ **只抽实体，不建独立 EventNode** | 这是用户/组织的知识背景，对后续推理有价值，但本身不是"发生" |
| **L2：情景化知识**  | 在特定交互中被激活/使用的知识 | "用户这次用 pandas 的 dtype 参数解决了 CSV 问题"     | ✅ 抽实体 + 建 EventNode        | 这才是情景记忆的核心——**谁在什么时候知道/使用了什么**  |

你说的"用户知道/关心的事实"恰好对应 **L1 和 L2 的合集**——它们区别于 L0 的本质是：**这些事实在用户的交互上下文中被激活了，代表用户的知识状态或关注点。**

### 具体操作建议

**对于 L0 过滤**——可以在 GLiNER/小参数LLM Layer 1 之后加一个轻量级规则层：
- 如果抽出的实体 + 关系在常见知识库中有完全匹配（如 Wikidata 的高频三元组），且没有用户个性化修饰（"我习惯用"、"我们团队用"、"上次用的"），则跳过不入图
- 这个过滤不需要很精确，宁可多抽不遗漏，因为后续 SemanticCluster 和检索时的排序会自然降权低价值实体

**对于 L1（用户声明的背景知识）**——这其实对应你现有设计中 EventNode 类型讨论里提到的"纯信息传递"问题（7.2节）：
- "我们的数据是按天分区的"
- "这个项目用的是 Python 3.10"

我建议这类信息：**抽实体（RESOURCE/TOOL/CONCEPT），建关系边，但不一定要建 EventNode**。它们的价值在于丰富实体之间的关系网络（语义记忆），而不是成为情景记忆的时序节点。如果硬要建 EventNode，type 又不好归——这正是你文档里方案 C（先不扩展类型，看"不抽事件但抽实体/关系"是否够用）的正确性所在。

**对于 L2（情景化知识）**——全量抽取，这是图谱的核心价值。

### 一句话总结 EntityNode 粒度

> **不是所有提到的实体都入图，而是"在交互中被激活、反映用户知识状态或操作对象的实体"才入图。通用常识是噪声，领域背景知识入实体层但不入事件层，情景化知识全量抽取。**

## 二、EventNode 抽取粒度：RawBlock 要不要变大？

这个问题的答案是：**RawBlock 不需要变大，但抽取逻辑需要从"turn 驱动"变成"语义驱动"。**

你现有的文档里其实已经有了答案（《 [[EventNode 抽取策略反思与改进方案]] 》），但我把核心逻辑拎出来，从你的问题角度重新组织。

### 为什么"把 RawBlock 变大"不是正确方向

假设把 RawBlock 从 1 turn 扩大到 5 turns：

| 你期望解决的问题        | 实际会发生什么                                                                               |
| --------------- | ------------------------------------------------------------------------------------- |
| 减少 EventNode 数量 | ❌ 如果5轮里有3个独立主题，LLM 仍然应该抽出3个 EventNode——否则就是信息丢失                                       |
| 降低图谱复杂度         | ❌ EventNode 数量由"有多少次有价值的发生"决定，不由 Block 大小决定                                           |
| 获得更好的上下文        | ⚠️ 部分成立——LLM 看到更多上下文确实能做更好的语义判断，但这可以通过 sliding window/context carry 实现，不需要改变 Block 定义 |
| 避免碎片化事件         | ❌ 碎片化的根因是"每个 turn 机械映射一个 EventNode"，不是 Block 太小                                       |

**核心洞察**：RawBlock 的粒度决定的是"信息的存储边界"和"溯源的最小定位单元"，而 EventNode 的粒度决定的是"语义的组织边界"。两者是解耦的。

你在切块讨论文档里已经说清楚了：

> **传统 RAG 靠"切块"来组织语义边界，你们靠"抽取"来组织语义边界。**

所以把 Block 变大，本质上是在用传统 RAG 的思路（调整 chunk size）来解决 Graph KG 的问题——方向不对。

### 正确的做法：控制 EventNode 的"入图门槛"

你的《 [[1. EventNode抽象的必要性]] 》文档里有个核心原则——**"最小 EventNode"：只把高价值、可复用、可推理、可检索的事件提炼出来**。

把这个原则操作化：

**不建 EventNode 的情况（过滤掉的低价值 turn）：**
- Assistant 的纯礼节/确认回复："好的"、"收到"、"我来看看"
- 用户的简单确认："嗯"、"对"、"继续"
- 信息传递型陈述（归入 L1 层，只抽实体不建事件）

**合并多 turn 为一个 EventNode 的情况：**
- 连续 2-3 轮在补全同一个请求（如订票场景的多轮澄清）
- 此时 EventNode 的 `source_block_ids` 记录所有来源 Block

**从一个 turn 拆出多个 EventNode 的情况：**
- 用户一句话包含多个独立语义单元（"dtype 问题解决了，但日期列还有问题"→ 一个 solution + 一个 problem）

这样，EventNode 的数量不是由 turn 数决定的，而是由**"有多少次有意义的发生"**决定的。你的反思文档里的那句话是最准确的：

> **不是"一 turn 一 event"，而是"一发生一 event"。**

### 量级估算：控制后的 EventNode 密度

假设一个典型的 30-turn Agent 会话：

| Turn 类型 | 数量 | 产出 EventNode | 说明 |
|----------|------|---------------|------|
| 用户请求 | ~5-6 | 5-6 个 | 每次有意义的意图转换 |
| 用户补充/澄清 | ~5-6 | 合并到相关请求 | 不独立建 |
| Assistant 确认/礼节 | ~8-10 | 0 | 过滤掉 |
| Assistant 方案/解决 | ~4-5 | 3-4 个 | solution/decision |
| 工具调用+结果 | ~6-8 | 3-4 个 | tool_use（不是每次调用都有记忆价值） |
| **总计** | 30 turns | **~12-15 个 EventNode** | 压缩比 ≈ 2:1 到 2.5:1 |

这个密度是合理的——一个 30 轮会话产出 12-15 个有价值的情景节点，每个都带明确的参与者、时间和语义类型，通过 PRECEDES 串成时序链。

### 另一个你可能还没考虑到的维度：Trace 侧的粒度

Trace 侧的问题和 Session 侧不同。Trace 日志天然是结构化的，一个 tool_use + tool_result 就是一对，不存在"语义模糊"的问题。真正的粒度问题在于：**是否每次工具调用都要建 EventNode？**

我建议不是。考虑这个场景：Agent 在一次排查中连续调用了 `read_csv` → `head()` → `dtypes` → `describe()`，4次工具调用。每次都建 EventNode 吗？

**建议**：对重复性/探索性工具调用做聚合——只保留"有状态变化意义"的调用（第一次调用、出错的调用、最终成功的调用、产出 artifact 的调用），中间的"纯查看"调用可以只保留 RawBlock 不建 EventNode。这也是"最小 EventNode"原则在 Trace 侧的体现。

## 三、回到你的核心问题：太细还是太粗？

你的直觉"太细会导致图谱过于复杂"是对的。但解决方案不是"让切块变粗"（改变 RawBlock 粒度），而是**让抽取变聪明**——用语义门槛控制什么值得成为节点。

```
                    RawBlock 粒度（存储边界）
                    │
                    │  保持 turn 级别不变
                    │  → 保证溯源精度
                    │
                    ▼
               ┌─────────┐
               │ LLM 抽取 │ ← 语义驱动，不是 turn 驱动
               └─────────┘
                    │
          ┌────────┼────────┐
          ▼        ▼        ▼
     EntityNode  EventNode  过滤掉
     (L1+L2)    (仅L2)    (L0+低价值turn)
```

**RawBlock 是存储和溯源的粒度，EventNode 是记忆和推理的粒度。两者解耦，各自优化。**
