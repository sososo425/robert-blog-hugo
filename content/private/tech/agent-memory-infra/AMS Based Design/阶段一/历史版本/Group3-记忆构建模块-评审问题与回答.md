# Group3 记忆构建模块 - 评审问题与回答

> [!info] 文档用途
> 本文档用于配合 [[Group3-记忆构建模块-详细方案设计-评审版]] 参加内部评审。
> 
> 目标不是提供“唯一标准答案”，而是帮助在评审现场快速、稳定地回答高概率问题，并始终把讨论收敛回 **本期原型边界、核心验证目标、实现取舍** 三个重点。

> [!tip] 回答总策略
> 建议按下面的顺序回答：
> 1. **先讲本期目标**：我们本期要验证什么
> 2. **再讲为什么这样设计**：为什么不用更重方案、为什么做这个取舍
> 3. **最后讲后续演进**：哪些能力是 Phase 2 再做
> 
> 这样可以避免评审讨论被带到“大而全架构”里去。

## 一、定位与边界类问题

### 1. 为什么 Group 3 要用知识图谱，而不是只用向量库？

**一句话答法**

向量库擅长“像不像”，但 Group 3 这期要验证的是“过去发生了什么、先后顺序如何、和哪些实体/事件相关”，这类问题更依赖图谱的关系和时序组织能力。

**展开回答要点**

- 本期输入是 Session / Trace，这类数据天然有**事件、关系、时间线**三个维度。
- 仅靠向量召回，难稳定回答：
  - 某个工具今天又在哪个事件里被用过？
  - 某个报错之前发生了什么？
  - 一个问题是如何从报错演化到解决方案的？
- 因此本期采用：
  - **Milvus** 负责相似候选召回和简单消歧
  - **Temporal KG / Neo4j** 负责关系、路径、时间线组织
- 所以不是“图谱替代向量”，而是**图谱负责结构，向量负责增强**。

---

### 2. 为什么本期强调 Temporal KG，而不是普通关系图？

**一句话答法**

因为 Agent Memory 的价值不只在于“谁和谁有关”，更在于“什么先发生、什么后发生、问题如何演化”。

**展开回答要点**

- 普通关系图更偏静态关联，适合回答“A 和 B 是否有关”。
- Group 3 当前更关心：
  - session 内事件顺序
  - trace step 顺序
  - 用户请求到执行链之间的桥接
- 所以本期最小能力必须包含：
  - `EventNode`
  - 时序边
  - timeline 查询
  - source block 溯源
- 这里的 Temporal KG 是**最小可用时序图谱**，不是一上来就做复杂时序推理系统。

---

### 3. 本期到底交付什么？又明确不交付什么？

**一句话答法**

本期交付的是一个能把 Session / Trace 转成结构化记忆、写入最小时序图谱、并支持本地查询验证的原型闭环；不交付完整检索层、复杂推理和生产级平台能力。

**展开回答要点**

- 本期交付重点：
  - `Session/Trace -> Raw Block -> Entity/Event/Temporal Relation -> Temporal KG`
  - 最小图模型
  - 本地查询验证
  - 轻量评估结果
- 本期明确不做：
  - 完整检索服务化
  - 多跳图推理框架
  - 社区发现
  - 自动冲突修复 / 自动遗忘
  - 全局统一 Memory 平台
- 评审时如果有人继续往大系统扩展，可以直接拉回 [[Group3-记忆构建模块-详细方案设计-评审版#1.3 本期明确不做的内容]] 和 [[Group3-记忆构建模块-详细方案设计-评审版#10.2 本期取舍原则]]。

---

## 二、数据与流程类问题

### 4. 为什么前期先用公开数据集，而不是直接接真实 Agent Framework 数据？

**一句话答法**

因为当前阶段最重要的是先把 Group 3 的处理闭环跑通，而公开数据集可以作为代理输入源，帮助我们在真实联调前完成开发、调试和 demo 验证。

**展开回答要点**

- 公开数据集的角色分两阶段：
  1. 开发 / 调试阶段：做流程测试集
  2. 原型稳定 / demo 阶段：做代理业务输入源
- 这样做的好处是：
  - 不依赖 Group 1 联调也能独立推进
  - 可以先把 schema、抽取、时序边、入库链路跑通
  - 等真实 session / trace 到位后，只需要做数据源替换验证
- 所以这不是“永远不用真实数据”，而是**先用代理源完成闭环，再用真实数据做替换验证**。

---

### 5. Session 和 Trace 为什么不直接混成一条链路？为什么又不完全拆成两套系统？

**一句话答法**

因为两者原始信号完全不同，所以前半段必须分开处理；但它们共同构成一条任务记忆，所以在统一记忆对象层和图谱层必须汇合。

**展开回答要点**

- Session 更关注：
  - 用户意图
  - 问题演化
  - 指代和上下文连续性
- Trace 更关注：
  - tool / action / status / latency
  - 执行链顺序
  - 错误 / 重试 / 产物
- 如果一开始就完全混合，会丢失各自信号；如果完全拆两套系统，又无法回答：
  - 某个请求触发了哪些执行步骤？
  - 某个报错在对话中提出后，是在哪个 trace step 里处理的？
- 所以本期采用：**前分后合，双链路处理，单图谱融合**。

---

### 6. `session` 和 `episode` 到底是什么关系？本期必须实现 `episode` 吗？

**一句话答法**

本文把 `session` 作为归并后的任务会话主单元，把 `episode` 作为 session 内更细的子段；但如果时间不足，本期原型可以先只实现 `session` 级归并。

**展开回答要点**

- `session`：一次归并后的任务会话主单元
- `episode`：session 内基于任务切换、时间间隔、结束信号等切出的子段
- 这样定义的好处是：
  - 后续可支持更细粒度事件组织
  - 当前又不强制一开始把粒度做得太细
- 评审时建议明确说：
  > `episode` 是保留的增强位，不是卡住本期验收的前置条件。

---

## 三、对象模型与存储类问题

### 7. 为什么 `SessionContext` 不直接作为节点？

**一句话答法**

因为在本期原型里，session 更适合作为上下文组织概念，而不是图谱主节点；主节点应该聚焦在真正承载长期记忆价值的 `EntityNode`、`EventNode` 和 `RawBlockRef`。

**展开回答要点**

- `session_id` 当前已经足够支撑：
  - 同 session 时间线查询
  - 同 session 事件聚合
  - Session / Trace 桥接
- 如果过早把每个 session 都建成节点，会增加图复杂度，但不一定提升本期 demo 价值。
- 因此当前收敛为：
  - `SessionContext` 主要由字段承载
  - 会话容器节点作为后续可选扩展
- 这样更符合“原型先最小闭环、后续再增强”的原则。

---

### 8. 为什么默认只持久化 `PRECEDES`，而不同时持久化 `FOLLOWS`？

**一句话答法**

因为两者本质上是同一时序关系的正反视角，原型期默认只持久化一类主持久化边，可以避免双写冗余、去重复杂度和一致性问题。

**展开回答要点**

- 本文约束是：
  - `PRECEDES`：主持久化时序边
  - `FOLLOWS`：查询视角 / 派生关系
- 这样设计的原因：
  - 简化入库逻辑
  - 降低重复边风险
  - 避免双向边一致性维护成本
- 如果评审问“那为什么正文里还提到 `follows`？”
  - 可以回答：`follows` 仍然保留为**语义关系名和查询视角**，但默认不作为主持久化边落库。

---

### 9. 为什么是 Neo4j + Milvus，而不是一个更统一的存储层？

**一句话答法**

因为本期目标是验证记忆构建闭环，而不是验证统一存储平台；`Neo4j + Milvus` 已经足够覆盖关系组织和相似召回两个核心需求。

**展开回答要点**

- Neo4j 解决：
  - 关系
  - 路径
  - 时间线
  - 溯源关联
- Milvus 解决：
  - 实体相似候选召回
  - 简单实体消歧增强
- 如果再引入统一 Storage SDK / 更多后端：
  - 工程复杂度会明显上升
  - 对本期 demo 收益有限
- 所以本期存储策略是：**最小必要而非平台完备**。

---

### 10. 为什么不直接照搬 Zep / Graphiti 的对象命名和全套设计？

**一句话答法**

我们借鉴它们的工程思想，但不直接照搬命名体系，因为当前更重要的是形成适合本项目分工、接口和原型目标的最小落地模型。

**展开回答要点**

- 借鉴的主要是：
  - provenance first
  - temporal fact
  - resolution / update 思想
  - hybrid retrieval 思路
- 不直接照搬的原因：
  - 当前已有 TL 统一的 Raw Block / ID 规范
  - Group 3 需要与本项目上下游接口对齐
  - 外部框架命名直接引入，容易让评审把重点转移到“名词对齐”而不是“闭环可行性”
- 所以推荐口径是：
  > 借鉴思想，不机械迁移命名。

## 四、评估与风险类问题

### 11. 如果实体链接、时间抽取没有做到很高精度，这个原型还有价值吗？

**一句话答法**

有价值，因为本期原型验证的重点不是追求 SOTA 指标，而是验证记忆构建主链路是否成立、是否可查询、是否可解释。

**展开回答要点**

- 本期不是打榜型项目，重点是：
  - 流程跑通
  - 图谱可写入
  - 查询可展示
  - 结果可回溯
- 因此评估关注的是：
  - 抽取质量是否达到“可演示”门槛
  - 时序边是否基本可信
  - demo case 是否能稳定回答
- 口径上可以明确说：
  > 本期要求的是“最小可用 + 可验证”，不是“全面最优”。

---

### 12. 如何避免“伪记忆”或不可解释的错误记忆？

**一句话答法**

靠的不是模型自信，而是**证据溯源 + 显式结构化 + 低置信度保留标记**。

**展开回答要点**

- 每个事件应能回溯到 `source_block_id`
- 实体和关系保留来源 block
- 时间不确定时允许 `null` 或低置信度标记
- 冲突和误合并本期不自动修复，但要保留可追查路径
- 这样即使结果不完美，系统仍然是**可解释、可核验、可调试**的，而不是黑盒“回忆”。

---

### 13. 与 Group 1 / Group 2 最终怎么衔接？为什么现在还能先独立推进？

**一句话答法**

因为版本 3 的横向分工允许各组先对自己的数据类型跑通端到端闭环；Group 3 当前先用公开数据和 mock 数据验证处理链路，后续再与 Group 1 / Group 2 做增强联调。

**展开回答要点**

- 当前独立推进并不等于忽略联调，而是为了降低前期依赖。
- 先独立跑通的价值：
  - 更快暴露 Group 3 自己的问题
  - 更早稳定接口和字段要求
  - 联调时不至于双方都在同时排查不确定问题
- 后续衔接方式：
  - Group 1：提供归档后的真实 session / trace
  - Group 2：可选提供标准化知识 block 作为补充输入
- 所以是：**先独立闭环，后联调增强**。

---

### 14. 评审如果质疑“为什么不直接做检索层 / Graph RAG / 多跳推理”，怎么回答？

**一句话答法**

因为如果底层记忆构建都还没稳定，先做检索层只会把问题往后推；本期应先证明“记忆能被正确构建、存储、查询和溯源”，再谈更上层检索与推理。

**展开回答要点**

- 检索层依赖底层对象质量：
  - schema 稳定
  - 关系可信
  - 时序可用
  - 溯源完整
- 如果这些都不稳，Graph RAG / 多跳推理只会放大噪声。
- 所以当前路线是：
  1. 先做记忆构建最小闭环
  2. 再做本地查询验证
  3. Phase 2 再考虑检索层和高级推理
- 这不是放弃检索，而是**按依赖顺序推进**。

---

### 15. 本次评审最应该看什么，而不应该被哪些点带偏？

**一句话答法**

最应该看的是这条链路能否形成最小可验证闭环；不应该过早被完整产品化、统一平台化或外部框架命名带偏。

**展开回答要点**

- 建议评审重点看四件事：
  1. 目标边界是否清楚
  2. 对象模型是否足够支撑原型
  3. Pipeline 是否能落到可实现步骤
  4. 验证与交付物是否闭环
- 不建议在本轮过早展开：
  - 统一 Memory SDK
  - 多后端编排
  - 社区发现
  - 完整检索层
  - 复杂自动修复
- 如果现场讨论跑偏，可以用一句话收口：
  > 这些方向我们认同，但它们属于后续演进，不是本期原型验收项。

## 五、评审现场可直接使用的收口句

### 1. 当讨论开始膨胀时

> 我们这版方案有意把问题收敛到“结构化记忆能不能稳定构建出来”，而不是一上来覆盖完整 Memory 平台。

### 2. 当有人追问为什么不做更多能力时

> 不是这些能力不重要，而是它们依赖底层记忆对象、时序关系和溯源机制先稳定下来。本期先验证底座，后续再叠检索和推理。

### 3. 当有人担心当前方案不够“高级”时

> 我们当前优先的是“可落地、可验证、可演示”，不是“概念最全”。对原型阶段来说，闭环比复杂度更重要。

### 4. 当有人质疑公开数据集是否足够真实时

> 公开数据集当前承担的是代理输入源角色，目标是先把 Group 3 的链路跑通；等 Agent Framework 数据就绪后，我们会做真实数据替换验证。
