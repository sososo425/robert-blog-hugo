## 问题 2：Encoder 路线处理中文，业界有方案吗？还是都放弃了？

**结论先行：没有放弃，但分成了两条完全不同的路。**

### 为什么 GLiNER 对中文差？—— 问题的精确定位

我们之前的实验中 GLiNER 中文表现差，**根因不是 "Encoder 模型做不了中文 NER"，而是 "多语言零样本 Encoder + BPE 分词" 这个特定组合做不好中文 NER**。这是一个很关键的区分：

```
GLiNER 中文失败 = 三个因素叠加的结果
│
├── 1. 分词方式错配
│   BPE/SentencePiece 把中文拆成字节级 sub-token
│   "张三" 可能变成 3 个 sub-token → span 边界对齐出错
│   而中文原生编码器（Chinese-BERT-wwm）每个中文字 = 1 token，完美对齐
│
├── 2. 训练数据偏斜
│   GLiNER-multi 的多语言训练数据中，中文占比远低于英文/欧语
│   导致中文上的 span 预测头"没见过足够多的中文模式"
│
└── 3. 零样本 + 宽标签的固有天花板
    24 类标签在零样本模式下互相竞争
    对于中文短句这种信息密度低的输入，竞争尤其激烈
```

### 中文 Encoder NER 的正确打开方式

中国 NLP 社区其实有一套**成熟且经过大规模生产验证**的 Encoder NER 方案体系，只是和 GLiNER 走的不是同一条路：

| 层次               | 代表                                                          | 核心差异（vs GLiNER）                               | 中文 NER F1                                 |
| ---------------- | ----------------------------------------------------------- | --------------------------------------------- | ----------------------------------------- |
| **中文原生预训练编码器**   | Chinese-BERT-wwm-ext、ERNIE 3.0-Base、MacBERT、RoBERTa-wwm-ext | **字级分词**：每个中文字 = 1 token，NER 标签对齐完美           | —                                         |
| **中国特色 NER 解码头** | **GlobalPointer**（苏剑林）、**W2NER**（AAAI 2022）                 | 用 span (start, end) 对代替 BIO 序列标注，天然支持**嵌套实体** | MSRA: **96.0-96.5%**；CLUENER: **~80-82%** |
| **中文联合抽取**       | **GPLinker**（苏剑林）、OneRel、TPLinker                           | 一步出实体+关系，避免管道式错误传播                            | 领域微调后 RE: **85-92%**                      |

**一句话总结**：中文 Encoder NER 的正道是 **中文原生编码器 + GlobalPointer/GPLinker**，**不是** 拿多语言 GLiNER 硬套。

**生产案例**：

- **百度搜索**：ERNIE-Base 做 NER，日处理数十亿查询
- **阿里电商**：StructBERT + 领域微调，商品实体抽取
- **京东、美团**：BERT-based NER 用于商品/门店/地址等封闭域实体

==**但有一个核心前提：这些方案都需要标注数据做微调**。==它们不是零样本的。

### 那 AMS 能走这条路吗？

| 条件 | AMS 现状 | 评估 |
|------|---------|------|
| 有标注数据？ | ❌ 目前无 | 需要先积累 |
| Schema 封闭？ | ⚠️ 部分封闭（6-8 类实体，6-14 类关系） | 可以，但开放关系仍需 LLM |
| 中英混合？ | ✅ 常见 | Encoder 弱项，需路由或用 LLM |
| 有精力维护专用模型？ | ❓ 取决于团队 | 微调+部署+迭代有持续成本 |

**我的判断**：

> **短期**（无标注数据阶段），走 Encoder 微调这条路**投入产出比不高**——你需要先标注数据、训练模型、部署服务，而 Qwen2.5-7B 用 prompt 就能达到 85-92% F1。
> 
> **中长期**（如果 AMS 日处理量达到万级以上），可以考虑 **LLM 标注 → 人工校验 → 蒸馏到 GlobalPointer** 的路线——先用 LLM 自动标注一批数据，人工校验后用来微调小模型，这是业界的标准降本路径。

### 中英混合怎么办？

==这是个真正的难题，目前**没有完美方案**：==

| 方案 | 优点 | 缺点 |
|------|------|------|
| XLM-R / ERNIE-M（跨语言编码器） | 同时处理两种语言 | 两种都不是最优 |
| 语言检测 + 路由到专用模型 | 各自最优 | 增加系统复杂度；句内混合无法路由 |
| **直接用 LLM** | 天然处理混合文本 | 成本和延迟较高 |

==**实话实说**：对于 AMS 这种"科技领域对话+中英混杂"的场景，**LLM 是处理中英混合最自然的选择**。Encoder 路线在句内中英混合上至今没有令人满意的解决方案。==

## 问题 3：文档知识库 GraphRAG 是不是完全开放域，必须拥抱 LLM？

**这个问题的答案取决于一个关键变量：你的 Schema 是预定义的还是开放的。**

### 开放域 vs 封闭域：判定矩阵

|  | 封闭域（Fixed Schema） | 开放域（Unbounded Schema） |
|--|----------------------|--------------------------|
| **实体类型** | 已知、有限（5-50 类） | 未知、会涌现新类型 |
| **关系类型** | 预定义（USES, CAUSED_BY…） | 无法预定义，需发现 |
| **训练数据** | 可标注或已有标注 | 无法预标注 |
| **Encoder 可行性** | ✅ **很好**。微调后的 BERT > LLM | ❌ 无法泛化到未见类型 |
| **LLM 必要性** | 大材小用但能做 | ✅ **必需**。唯一能做 schema-free 抽取的 |
| **典型场景** | 电商商品KG、医疗病历KG、AMS 记忆 | **文档知识库 GraphRAG** |

### 文档知识库 GraphRAG 为什么是"准开放域"

以 Microsoft GraphRAG 为例，它对任意文档做 KG 构建时面临的挑战：

```
一篇关于"量子计算在药物发现中的应用"的论文
│
├── 实体类型完全无法预定义
│   "量子退火算法"→ 什么类型？METHOD? TOOL? CONCEPT?
│   "辉瑞"→ ORG（这个能）
│   "分子对接"→ TECHNIQUE? CONCEPT? ACTION?
│
├── 关系类型同样无法穷举
│   "量子退火算法 用于 分子对接" → USED_FOR? APPLIES_TO? ENABLES?
│   这些关系是论文的语义决定的，不是预先能列完的
│
└── 跨段落的隐含关系
    "第2节讲了方法，第5节讲了该方法的局限性"
    → 需要理解上下文才能建立 LIMITS 关系
```

**所以 Microsoft GraphRAG 用 GPT-4 做全部抽取，没有 Encoder 参与**。这不是技术偏好，而是**任务性质决定的**。

### 但也不是"完全没有 Encoder 的空间"

一个更精确的回答是——**取决于你怎么用 GraphRAG**：

| 使用方式 | Schema 性质 | 推荐方案 |
|---------|------------|---------|
| **通用文档 KG**（任意文档扔进去自动建图） | 完全开放 | **纯 LLM**（GraphRAG 原版方案） |
| **垂直领域文档 KG**（如只处理法律合同/医疗病历） | 半封闭 | **Encoder NER + LLM RE**（混合） |
| **有固定 Schema 的知识库**（如产品手册→产品属性图谱） | 封闭 | **Encoder 为主，LLM 补边** |

### AMS 记忆 vs 文档 GraphRAG 的对比

| 维度 | AMS 记忆 | 文档知识库 GraphRAG |
|------|---------|-------------------|
| 实体类型 | **半封闭**：TOOL, PERSON, CONCEPT, RESOURCE, ORG, ACTION（6-8类） | **开放**：无法预定义 |
| 关系类型 | **半封闭**：USES, INVOKES, PRODUCES 等 + 允许 LLM 生成新类型 | **开放**：完全由文档内容决定 |
| 文本特征 | 对话/日志，模式相对固定 | 任意文档，高度异构 |
| Encoder 可行性 | ⚠️ 理论可行（封闭部分），实操受限于中文 | ❌ 基本不可行 |
| LLM 必要性 | 中（可用于精修+开放关系） | **高**（主抽取器） |

> **你的直觉是对的**：AMS 的"半封闭域"性质确实给了 Encoder 线一定的生存空间（尤其是英文 Trace 部分）；而文档知识库 GraphRAG 因为完全开放域，基本上必须拥抱 LLM 路线。

### 一个值得思考的中间路线

即使在 GraphRAG 场景中，也有人在探索**混合方案**来降本：

```
文档输入
  │
  ├── Phase 1: Encoder 快速扫描（可选）
  │   中文原生 BERT + GlobalPointer
  │   → 抽出"显而易见"的实体：人名、组织、地名、日期
  │   → 成本: ~$0，延迟: ~10ms
  │   
  ├── Phase 2: LLM 深度抽取
  │   Qwen2.5-7B / GPT-4o-mini
  │   → 以 Phase 1 实体为锚点，抽取关系 + 发现新实体
  │   → prompt 中注入已知实体，减少 LLM 重复工作
  │   
  └── Phase 3: LLM 社区发现 + 摘要（GraphRAG 特有）
      → 这步完全是 LLM 的活
```

**这个方案的逻辑**：Phase 1 的 Encoder 不是为了替代 LLM，而是为了**给 LLM 提供锚点、缩短 prompt、减少幻觉**。类似于你们 AMS 设计文档中"先验锚点"的思路，只不过不再把 Encoder 当作"主力"。

## 总结：三个问题的统一答案

```
                    封闭域 ←————————————→ 开放域
                     │                      │
            Encoder 可以主导          LLM 必须主导
            (但需要微调 +             (Encoder 只能做锚点)
             中文原生编码器)
                     │                      │
              ┌──────┘                      └──────┐
              │                                     │
         AMS 记忆（半封闭）              文档 GraphRAG（开放）
         • 英文 Trace: Encoder ✅       • 必须 LLM
         • 中文 Session: 小 LLM ✅      • Encoder 仅可选辅助
         • 复杂推理: 大 LLM ✅          • 大 LLM 为主
```

**对你三个问题的直接回答**：

1. ✅ 小 LLM 方向正确，值得优先投入
2. **Encoder 处理中文有方案，但不是 GLiNER 那条路**——是中文原生编码器（Chinese-BERT-wwm）+ 中国社区的 GlobalPointer/GPLinker，需要标注数据微调。AMS 短期不具备条件，中长期可用"LLM 标注→蒸馏到小模型"的路径
3. **文档 GraphRAG 基本是开放域，必须拥抱 LLM**。但可以用 Encoder 做快速锚点来辅助 LLM（降本增质），不是完全没有 Encoder 的价值

## 问题3：方案 B 中"NLI 补边"具体在干什么

回到方案 B 的流程图：

```
原文 → 切段 → GLiNER NER(抽实体) → GLiNER-RelEx(联合抽实体+关系) → 规则过滤 → NLI补边 → 输出
```

前面的 GLiNER-RelEx 已经输出了一些关系（如 `FLIES_FROM`, `FLIES_TO`），但它的关系类型是**模型训练时固定的那 14 类**，覆盖不了 AMS 需要的所有语义关系。

**NLI 补边做的事**：对 RelEx 没覆盖到的实体对，用 NLI 模型"**再扫一遍**"，尝试补充额外的关系边。

具体步骤：

### Step 1：构造实体对

从前面 NER + RelEx 输出的所有实体中，取**两两组合**（排除已有 RelEx 关系的对）。

比如 NER 抽到了 `张三`、`支付宝`、`菜市场`，RelEx 只给出了 `张三 → 菜市场` 的关系，那 `(张三, 支付宝)` 和 `(支付宝, 菜市场)` 就是待补的实体对。

### Step 2：为每个实体对构造假设模板

方案 B 预定义了 **11 类关系**，每类对应一个中文假设句模板：

| 关系类型 | 假设模板（举例） |
|---------|--------------|
| USES | "{A} 使用 {B}" |
| PAID_WITH | "{A} 通过 {B} 完成支付" |
| LOCATED_IN | "{A} 位于 {B}" |
| OWNS | "{A} 拥有 {B}" |
| ... | ... |

对于实体对 `(张三, 支付宝)`，会生成 11 个假设句：
- "张三 使用 支付宝"
- "张三 通过 支付宝 完成支付"
- "张三 位于 支付宝"
- ...

### Step 3：NLI 模型打分

把**原文作为前提 (premise)**，每个假设句作为 **hypothesis**，送进 mDeBERTa-xnli 模型。模型输出三个概率：

```
entailment:    0.82   ← 原文支持这个假设
neutral:       0.15   ← 原文与假设无关
contradiction: 0.03   ← 原文反驳这个假设
```

取 `entailment` 分数最高且超过阈值的那个关系，作为这对实体之间的补充关系。

### Step 4：输出补边

如果 `"张三 通过 支付宝 完成支付"` 的 entailment 分 = 0.82（最高且过阈值），就输出：

```
PAID_WITH(张三, 支付宝)   confidence=0.82
```

这条关系边被**"补"** 到了图谱里——RelEx 没抓到的，NLI 补上了。所以叫**"补边"**。

### 核心瓶颈

报告实验发现的关键问题：**如果上游 NER 漏了实体，实体对就构造不出来，NLI 再强也无边可补**。比如 `market_payment` 那条句子，GLiNER NER 只抽出 1 个实体（还是错的），0 个有效实体对 → NLI 输出 0 条关系。这就是经典的"管道式错误传播"。

## 问题4：mDeBERTa-xnli 有 ModernBERT 类替代方案吗？

调研结果：

### ModernBERT：有 NLI 微调版，但**不支持中文**

HuggingFace 上有两个 NLI 微调模型（2025 年 1 月发布）：

| 模型 | 参数量 | 英文 MNLI |
|------|--------|----------|
| `tasksource/ModernBERT-base-nli` | 149M | — |
| `tasksource/ModernBERT-large-nli` | 395M | 0.89 |

但 ModernBERT 预训练数据是**纯英文+代码（2T tokens）**，词表里没有中文。拿来跑中文假设模板 `"张三 使用 支付宝"` 基本等于乱码输入。**不可用于 AMS 的中文场景。**

截至目前，**没有多语言版 ModernBERT**。

### 真正可考虑的替代方案

| 模型 | 参数量 | 中文支持 | 特点 |
|------|--------|---------|------|
| **`MoritzLaurer/bge-m3-zeroshot-v2.0`** | 0.6B | ✅ 100+ 语言 | 同一作者(MoritzLaurer)的新作，基于 BGE-M3 多语言骨干，drop-in 替换当前模型 |
| **`IDEA-CCNL/Erlangshen-Roberta-330M-NLI`** | 330M | ✅ 纯中文 | CMNLI 82.25，中文专精 |
| **`IDEA-CCNL/Erlangshen-MegatronBert-1.3B-NLI`** | 1.3B | ✅ 纯中文 | CMNLI **84.52**，中文最强 NLI encoder |
| 当前：`mDeBERTa-v3-base-xnli` | 278M | ✅ 多语言 | XNLI-zh **80.3**，久经验证 |

### 小结

```
如果你继续用 NLI 补边方案（encoder 路线）：
├── 多语言场景 → 试 bge-m3-zeroshot-v2.0（同作者升级版）
├── 纯中文场景 → 试 Erlangshen-330M-NLI 或 1.3B 版
└── 求稳不换 → mDeBERTa-xnli 仍然是合理选择

但报告的核心结论是：
  NLI 补边的瓶颈不在 NLI 模型本身，而在上游实体对的质量。
  换更强的 NLI 模型，解决不了 "NER 漏实体→无边可补" 的问题。
```

所以如果走 encoder 路线优化，**优先级是修 NER（比如换中文专精 encoder），而不是换 NLI 模型**。不过根据之前的实验结论，小 LLM 路线（gemma4-e4b 那类）直接端到端输出实体+关系，从根本上绕过了这个管道传播问题。
