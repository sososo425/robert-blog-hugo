**5 项工作里有 4 项是 Group 1 的技术域**。Prompt Assembly 看起来跟 Group 4 有关，但本质上就是"拿 WM 数据 + 拿 Retrieval 结果 → 拼模板"，是一个很薄的胶水层，不需要深度理解检索逻辑。

## 调整建议

完全同意你的方案，做如下微调：

```
Group 1（模块 A + F）: 数据采集 & ETL + Working Memory
├── Phase 1-2: 专注 ETL Pipeline（模块 A），WM 仅做接口定义
├── Phase 2 末: 启动 WM 实现（Redis + Compact）
└── Phase 3:   完成 Prompt Assembly + Consolidation

Group 4（模块 E）: 检索服务 & 评估（专注）
├── 不再承担 WM 工作
└── Prompt Assembly 改为：Group 1 提供 WM 数据，Group 4 的 Retrieval API 接收
```

**Prompt Assembly 的接口边界：**
```
Group 1 负责：提供 GET /api/v1/memory/working-memory/{session_id}
             → 返回当前 WM 上下文（已 Compact 压缩）

Group 4 负责：Retrieval API 接收 session_context 参数（来自 WM）
             → 融合检索结果后返回

组装点：Agent Framework 侧，或一个薄的 API Gateway
       → 调 Group 1 的 WM API + 调 Group 4 的 Retrieval API → 拼装 Prompt
```

这样 Prompt Assembly 变成一个接口协作而非某个 Group 的内部工作，更干净。
