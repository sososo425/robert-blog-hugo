# AMS 陈述性记忆构建系统 — 概要设计

> 本文档是概要设计，描述系统的原理、思路和粗粒度方案。各章节的数据结构定义、Prompt 模板、代码实现等细节，请参阅对应的详细设计文档。

---

## 1. 系统定位与目标

### 1.1 我们要解决什么问题

Agent 每次对话都是"失忆"的——它不记得用户上周用 pandas 处理 CSV 时遇到了什么问题，也不知道"那个库"在这个用户的语境下通常指什么。本系统的目标是让 Agent 拥有**跨会话的长期记忆**，使其能够：

- **认识用户**：知道用户的技术栈、工具偏好、历史交互深度
- **回忆经历**：记得某次对话中问题是如何演化和解决的
- **理解指代**：当用户说"上次那个问题"时，准确定位到具体事件
- **举一反三**：遇到新问题时，联想历史上语义相似的经验

### 1.2 输入：Session 与 Trace — 同一交互的两个视角

系统的原始输入来自 Agent 运行时产生的两类数据：

| 视角 | Session（对话消息流） | Trace（执行日志） |
|------|----------------------|-------------------|
| 观察的是 | 用户与 Agent **说了什么** | Agent 内部**做了什么** |
| 组织中心 | 对话时间线（turn-based） | 执行树（span/step-based） |
| 典型内容 | 意图、问题、约束、决策 | 工具调用、状态、延迟、错误重试 |
| 语义密度 | 高（自然语言） | 低（结构化日志） |

**举例**：用户说"帮我读一下这个 Excel"（Session），Agent 内部调用了 `python_executor.read_excel(file="data.xlsx")`，耗时 420ms，返回成功（Trace）。两者缺一不可——Session 告诉你"用户想做什么"，Trace 告诉你"系统实际执行了什么"。

**为什么不合并处理**：Session 的核心难点在语义（指代消解、意图变化），Trace 的核心难点在结构（字段异构、执行链重建）。混合处理会让 pipeline 变得脆弱。

### 1.3 产出：语义记忆与情景记忆

本系统产出的是**陈述性记忆（Declarative Memory）**，包含两个子类型，直接映射认知心理学的经典模型：

**情景记忆（Episodic Memory）** — "当时发生了什么"
- 对特定事件的有时间戳的回忆
- 例：上次 CSV 列类型问题发生在哪个会话？read_excel 调用前发生了什么？

**语义记忆（Semantic Memory）** — "我知道什么"
- 跨会话稳定的实体、概念、关系认知
- 例：这个用户常用哪些工具？pandas 和 read_excel 之间是什么关系？

两者是**检索时的分工**，而非替代关系：
- 用语义记忆（实体 + 关系）做**语义索引** —— 定位"我在找什么"
- 用情景记忆（事件 + 证据）做**细节还原** —— "当时具体发生了什么"

> 这一分工借鉴了 HippoRAG（arXiv 2405.14831）的海马体记忆索引理论。

### 1.4 六类核心能力

系统建成后应能回答六类问题，覆盖四种核心用途：

| 用途           | 问题类型       | 举例                                                    |
| ------------ | ---------- | ----------------------------------------------------- |
| **知道用户是谁**   | 实体查询、路径查询  | "pandas 用户用过哪些功能？" / "read_csv 和 read_excel 之间有什么关联？" |
| **记得发生过什么**  | 时间线重建、因果追溯 | "那次对话中问题怎么从 CSV 类型错误演化到 dtype 修复的？"                   |
| **理解用户在说什么** | 跨会话指代解析    | "'上次那个问题'指的是哪个事件？"                                    |
| **联想相关经验**   | 语义联想       | "历史上有没有类似的数据文件类型识别问题？"                                |

### 1.5 系统边界

**包含**：输入适配 → LLM 抽取 → 实体去重 → Temporal KG 写入 → 实体画像 → 语义固化 → 混合检索 → 遗忘机制

**不包含**：Agent 框架本身、Working Memory（上下文窗口）、静态知识库、程序性记忆（Skill/工作流）、生产级多租户治理

## 2. 整体架构

### 2.1 全局数据流概览

系统的核心数据流分为**构建流程**和**检索流程**两条主线：

**构建流程**（从原始数据到知识图谱）：

```
Session / Trace 原始数据
  → Stage 0: 输入适配（格式归一化）
  → Stage 1: Raw Block 生成（统一原料格式，不做语义抽取）
  → Stage 2: LLM-Driven 混合抽取（实体 / 事件 / 关系，含时效推理）
  → Stage 3: 实体去重与链接（规则 → 向量召回 → LLM 判断）
  → Stage 4: Temporal KG 写入（Neo4j + Milvus + 归档层）
  → Stage 5: 实体画像积累（异步批处理，高频实体 Summary）
  → Stage 6: SemanticCluster 语义固化（跨会话主题聚类）
```

**检索流程**（从用户查询到原始上下文）：

```
用户查询
  → 三通道并行：向量通道(Milvus ANN) + 图谱通道(Neo4j Cypher + PPR 多跳) + 上下文过滤(tenant/session/时间窗)
  → 综合打分（RRF 融合）
  → 命中 EventNode → 溯源 RawBlockRef → 还原原始上下文
```

### 2.2 分层架构

| 层次 | 职责 | 执行方式 |
|------|------|---------|
| **输入适配层** | Session/Trace 归一化，Raw Block 生成 | 流式或批量，同步 |
| **抽取层** | LLM-Driven 实体/事件/关系抽取，实体去重 | 异步流水线 |
| **图谱存储层** | Temporal KG 写入，增量 Upsert，冲突处理 | 事务写入 |
| **画像层** | 实体 Summary 更新，用户偏好积累 | 异步批处理 |
| **语义固化层** | SemanticCluster 构建与维护 | 定时/阈值触发 |
| **遗忘层** | 时效衰减，低置信过期，显式覆盖 | 定时任务 |
| **检索层** | 混合检索，PPR 多跳，证据溯源 | 同步查询服务 |

### 2.3 "前分后合"双链路策略

这是本系统处理 Session 和 Trace 的核心策略：

```
Session 输入 → Session 链路（语义抽取）──┐
                                         ├→ 统一 Raw Block → 统一 Temporal KG
Trace 输入   → Trace 链路（结构抽取）──┘
```

**前端分离**：两条链路独立处理，各自面对不同的技术难点（Session 侧重语义理解，Trace 侧重结构解析）。

**后端融合**：两条链路最终写入同一张 Temporal KG。写入后，事件节点天然形成两个族群：
- **对话事件**（来自 Session）：user_request、problem、decision、solution
- **执行事件**（来自 Trace）：tool_use、tool_result、artifact_create

**粘合机制**：
- **EntityNode** 归一后天然跨族群 —— 同一个实体 `pandas` 不管从哪条链路抽出，都指向同一个节点
- **桥接边**（REQUEST_LEADS_TO / ATTEMPTS_TO_SOLVE / EVIDENCES）显式连接对话事件与执行事件之间的因果关系

### 2.4 三类存储的职责分工

| 存储 | 角色比喻 | 职责 |
|------|---------|------|
| **Neo4j** | 记忆的**骨架** | Temporal KG 主存储：节点、关系、时序、溯源 |
| **Milvus** | 记忆的**语义索引** | 向量索引：实体相似候选召回，辅助去重与检索 |
| **归档层（JSONL/OSS）** | 记忆的**原料仓库** | 原始内容持久化：Raw Block 原文、LLM 调用记录 |

## 3. 数据模型（Graph Schema）概要

### 3.1 四类核心节点

本系统的图模型遵循**最小够用原则** —— 4 类节点覆盖全部核心需求：

| 节点类型 | 所属记忆层 | 角色 | 一句话说明 |
|---------|----------|------|-----------|
| **EntityNode** | 语义记忆 | 持久对象 | 跨会话可归一的稳定实体（工具、概念、人、组织等），是连接不同情景的"粘合剂" |
| **EventNode** | 情景记忆 | 时序单元 | 有时间、有参与者、有状态的瞬时事件，是时序链的节点和溯源的锚点 |
| **RawBlockRef** | 情景记忆 | 证据锚点 | 轻量溯源节点，指向归档层的原始 Raw Block（不存全文） |
| **SemanticCluster** | 语义记忆 | 主题知识 | 对多个 EventNode 聚类后生成的语义摘要，实现"从碎片到主题"的固化 |

**举例说明它们如何协作**：

> 用户在 3 月 28 日的会话中说"帮我用 pandas 读一下这个 CSV"，Agent 调用了 `read_csv`，返回了一个 DataFrame。
>
> - `pandas`、`read_csv`、`CSV` → **EntityNode**（稳定实体，跨会话复用）
> - "用户请求用 pandas 读 CSV" → **EventNode**（对话事件，source_type=session）
> - "read_csv 调用成功，返回 128 行" → **EventNode**（执行事件，source_type=agent_trace）
> - 原始对话内容 → **RawBlockRef**（证据锚点，指向归档层 JSONL）
> - 一周后，多个类似事件被聚类为"pandas 数据文件读写问题排查" → **SemanticCluster**

### 3.2 五类边关系

| 边类别 | 连接 | 核心作用 |
|--------|------|---------|
| **A. 实体关系边** | Entity ↔ Entity | 语义记忆的核心内容，携带时间有效性（valid_at / invalid_at / superseded_at）和 Foresight 推理 |
| **B. 事件时序边**（PRECEDES） | Event → Event | 构建同一 session 内的时间线，只持久化单向边 |
| **C. 参与与溯源边** | Entity → Event, Event → RawBlockRef | 实体参与事件（PARTICIPATES_IN），事件溯源到原始证据（DERIVED_FROM） |
| **D. 桥接边** | Event → Event（跨来源） | 连接对话事件与执行事件的因果关系（REQUEST_LEADS_TO 等） |
| **E. 语义固化边** | Cluster → Event/Entity | Cluster 聚合了哪些事件，代表哪些核心实体 |

### 3.3 关键设计权衡

- **为什么需要 EventNode**：如果只用"实体 + 关系"建模，会丢失事件的发生顺序、多参与者关联、证据归属。EventNode 把"一次发生"变成图谱里的一等公民。
- **为什么不创建 SessionNode**：`session_id` 作为字段挂在 EventNode 上，避免不必要的图复杂度。语义层面的检索由 SemanticCluster 承载。
- **实体关系边用属性包（property bag）**：携带时效字段，而非为每种关系创建独立节点。

> 详细的节点属性定义、Cypher Schema、索引设计，参见各章详细设计文档。

## 4. 输入适配与 Raw Block 生成

> 详细设计参见：[第4章-输入适配与RawBlock生成-重构版.md](第4章-输入适配与RawBlock生成-重构版.md)

### 4.1 Raw Block：统一原料格式

Raw Block 是系统的**统一原料格式**，所有后续处理都以 Raw Block 为输入。每个 Block 只含原始内容和结构化元数据，不做任何语义提炼。

**设计思路**：无论 Session 还是 Trace，经过各自的归一化处理后，都产出结构一致的 Raw Block，实现"多种输入、统一处理"。

### 4.2 Session 链路的关键决策

**信任上游框架的 session 边界**：`session_id` 由上游 Agent 框架（如 Langflow）生成，AMS 直接采信，不自行切分。理由是：对接框架时 session 边界已确定，AMS 再切分是重复劳动且容易引入分歧。

**不做 episode 子段切分**：原方案预留了 `episode_id`，但经分析决定不实现。因为话题交织时硬切分会导致错误归属，而 Stage 6 的 SemanticCluster 通过异步软聚类天然解决了多话题分组问题，且支持跨 session 聚合。

**每个 Turn 生成一个 Raw Block**：保持 turn 原子性，不跨 turn 合并。

### 4.3 Trace 链路的关键决策

**适配器插件架构**：不同 Agent 框架（LangChain、AutoGen、自研框架）的 Trace 格式存在差异，通过适配器插件处理——每个框架对应一个适配器，新框架接入只需新增适配器，不修改主链路。

**每个 Step 生成一个 Raw Block**：保持 step 原子性，重试步骤各自生成独立 Block。

**核心难点**不在字段映射，而在**执行链重建**：某些框架的 Trace 是扁平列表需重建树状结构，错误重试需区分是重试还是新调用。

## 5. 混合抽取 Pipeline

> 详细设计参见：[第5章-混合抽取Pipeline-重构版.md](第5章-混合抽取Pipeline-重构版.md)

### 5.1 核心思路：按语言和数据源选最合适的模型

抽取任务（实体、事件、关系）采用 **"按路径分流、分层递进"** 的混合架构，而非全部依赖大 LLM：

| 路径 | 主抽取器 | 理由 |
|------|---------|------|
| **中文会话 Session** | 小 LLM（Qwen2.5-7B / gemma4-e4b） | 中文预训练充分，一次调用同时输出实体+关系+事件 |
| **英文 Trace / 结构化文本** | Encoder（GLiNER-RelEx） | 速度快（~20-40ms）、成本低、英文精度高 |
| **Foresight / 开放推理** | 大 LLM（GPT-4o / Claude） | 仅处理不可替代的子任务：时效推理、开放关系发现、因果推断 |

**为什么不用全 LLM 方案**：成本（~$300/天 vs 优化后 ~$30-50/天）和延迟（~3-6s vs ~40ms-2s）差异显著。

**为什么中文不用 Encoder（GLiNER）**：经实测验证，GLiNER 系列在中文会话场景表现远逊预期——无法正确抽取基础中文实体。根本原因是其预训练数据中中文覆盖不足，subword embedding 对中文字符的 span 边界检测能力从根本上缺失。

### 5.2 三层递进架构

```
Raw Block → Layer 0（路由判断）
  ├── Layer 1: 主抽取（小 LLM 或 Encoder，完成 50-80% 的结构化抽取）
  ├── Layer 2: 规则/轻量工具（停用词过滤、时间解析、aliases 聚合、类型校验，~5ms）
  └── Layer 3: 大 LLM 精修（仅不可替代子任务：Foresight 时效推理、fact_text 改写、开放关系发现）
```

**核心思想**：Layer 1+2 的输出作为 Layer 3 的**先验锚点**，大 LLM 从"全量抽取"变为"增强补充" —— prompt 更短、输出更稳定、成本大幅下降。

### 5.3 Foresight：事实有效期预测

这是本系统的设计亮点之一（借鉴 EverMemOS）：在抽取关系时，要求 LLM 主动推理每条事实的有效期预期。

**举例**：
- "用户正在使用 pandas" → `validity_reasoning = "Active in current session, may change"`
- "API Key = abc123" → `validity_reasoning = "Credentials typically expire, estimate 90 days"`，`invalid_at = 2026-06-28`
- "pandas 是 Python 数据处理库" → `validity_reasoning = "Stable semantic fact, unlikely to change"`

这为后续的遗忘机制提供了前置判断依据。该任务必须由大 LLM 完成——Encoder 模型无法进行链式推理和时效预测。

### 5.4 落地策略

分三个阶段渐进验证和替换，不是一步到位：
1. **验证期**：保持全 LLM pipeline，并行跑对比实验（GLiNER vs 小 LLM vs 大 LLM）
2. **优化期**：部署路由层，中文/英文路径分别替换 Layer 1
3. **深度优化**：只对复杂 block 调用大 LLM，简单 block 在 Layer 1+2 完成后直接写入

## 6. 实体去重与链接

### 6.1 问题本质

同一实体在不同会话中可能以完全不同的形式出现：`pandas` / `pd` / `Pandas` / "那个库" / "Python 数据处理库"。去重的目标是把这些指向同一真实对象的不同表述，归并到同一个 `entity_id` 下。

### 6.2 三层去重策略

```
新实体 → Step 1（规则归一化）→ Step 2（向量候选召回）→ Step 3（LLM Candidate-ID 判断）
```

**Step 1 — 规则归一化**（毫秒级）：大小写统一、去空格、常见缩写映射（`pd` → `pandas`）。这是唯一保留规则的环节。

**Step 2 — Milvus 向量候选召回**：在海量实体中快速召回相似候选（余弦相似度 > 0.85 的 top-5），缩小 LLM 判断范围。

**Step 3 — LLM Candidate-ID 模式**（借鉴 Graphiti）：用编号方案替代字符串匹配，让 LLM 做离散选择（"这个新实体匹配候选 [0]？[1]？还是 [-1] 全新？"），比开放式判断更稳定。

**核心原则：宁可漏合并，不可误合并**。漏合并只是多了冗余节点，误合并会导致完全错误的检索结果。

### 6.3 离线同义关系发现

实时去重处理的是明确的同名/别名。但"分布式追踪" vs "链路追踪" vs "Distributed Tracing" 这类**语义相似但表面不同**的实体，通过离线批处理发现：
- 定时扫描全量实体 → ANN 批量检索候选 → 精确相似度计算 → 生成 SYNONYM_OF 边
- 用途：检索时扩展召回，不作为实体归一的依据（避免误合并）

## 7. Temporal KG 写入

### 7.1 写入四原则

1. **溯源优先（Provenance First）**：每个 EventNode 和高价值关系边必须有 `source_block_id`，确保任何记忆都能追溯到原始输入
2. **增量 Upsert**：不是无脑追加，而是与已有节点比对后分情况处理（重复→更新、补充→扩充、冲突→旧事实标记 superseded_at 新事实写入、全新→创建）
3. **幂等性**：同一 `block_id` 多次写入，结果一致，不产生重复节点
4. **事务边界**：一个 Raw Block 的完整处理（实体+事件+关系）作为一个事务

### 7.2 冲突处理机制（superseded_at）

当新事实与旧事实冲突时（如用户从 pandas 切换到 polars），不删除旧事实，而是：
- 旧事实边标记 `superseded_at = 切换时间`
- 新事实作为新边写入
- 新旧并存，支持查询"用户曾经用过什么工具"

### 7.3 Session-Trace 桥接边

桥接边是"前分后合"策略的关键。构建采用分层策略：
- **最可靠**：Agent 框架层的显式关联（Trace 的 metadata 携带 session_turn_id），置信度 0.95+
- **Fallback 1**：时间邻近（<30 秒）+ 实体交集，置信度 0.75-0.85
- **Fallback 2**：执行结果与后续对话事件的语义匹配，置信度 0.70-0.80

### 7.4 PRECEDES 边的 O(1) 构建

写入服务在内存中维护每个 session 的 `latest_event_id`，新事件直接与上一事件连接，避免图库扫描。仅首条事件或历史修复时才触发一次 fallback 查询。

## 8. 实体画像积累

### 8.1 为什么需要画像

高频实体需要形成**稳定认知画像**，用于：
- 检索个性化排序（用户频繁使用的工具优先展示）
- 自动摘要生成（减少重复抽取成本）
- 偏好推断（识别工具使用习惯、技术栈倾向）

### 8.2 核心机制

**实体 Summary 自动更新**（借鉴 Graphiti 的 summarize_nodes）：
- 触发条件：usage_freq 达阈值 / 距上次更新超过时间窗 / 有新的高置信度关联事实
- 增量合并：保留稳定信息，更新时变信息，而非每次全量重写

**用户偏好画像**（独立 UserProfile 节点）：
- 由异步批处理任务对多个实体、事件和关系统计分析后生成
- 包含常用工具列表、技能领域推断、典型工作流模式

> 用户画像是跨实体聚合后的推断结果，不适合挂在单个 EntityNode 上，因此保留独立节点。

## 9. SemanticCluster：从情景碎片到语义主题

### 9.1 为什么需要语义固化

情景记忆（EventNode）是离散的事件点，随着数据积累会面临：检索效率低（需遍历所有 session）、模式难识别（分散事件实际是同一类问题的重复）、知识不沉淀。

**语义固化的目标**：将分散的情节碎片聚类提炼为稳定的语义主题，完成从"记得发生了什么"到"知道是什么类型的问题"的跃迁。

> 借鉴 EverMemOS 的 MemScene 概念和 GraphRAG 的 Community Summary 设计。

### 9.2 构建思路

**离线批处理**，触发条件为阈值（新增 EventNode > N）或定时（每日/每周）：
1. 获取待聚类的 EventNode
2. 生成事件 embedding（summary + participants 拼接）
3. HDBSCAN 层次聚类
4. LLM 为每个聚类生成主题名称和摘要
5. 创建 SemanticCluster 节点 + AGGREGATES 边

**增量维护**：新事件到来时，通过 Milvus ANN 召回候选 Cluster，相似度超阈值则并入，否则创建新 Cluster。Cluster embedding 采用成员 embedding 的滑动均值策略同步更新。

### 9.3 SemanticCluster 替代了 episode 切分

原方案预留的 episode 子段切分存在**话题交织无法处理**的硬伤。SemanticCluster 通过异步软聚类严格覆盖了 episode 的所有目标：

| 维度 | episode 切分 | SemanticCluster |
|------|:-----------:|:---------------:|
| session 内多话题分组 | ✅ | ✅ |
| 跨 session 同主题聚合 | ❌ | ✅ |
| 话题交织处理 | ❌（硬切导致错误归属） | ✅（软聚天然容忍） |

### 9.4 完整记忆路径

```
Session/Trace → Raw Block → EventNode（情景记忆：what happened）
                                ↓ 聚类 + LLM 摘要
                           SemanticCluster（语义记忆：what kind of problem）
                                ↓
用户查询 → 命中 Cluster → 展开相关 EventNode → 溯源 RawBlockRef → 原始上下文
```

检索时通常先命中语义记忆（定位主题），再展开情景记忆（查看细节）。

## 10. 检索层

### 10.1 三通道混合检索

不同查询类型需要不同策略，系统采用三通道并行 + 融合打分：

| 通道 | 引擎 | 擅长场景 |
|------|------|---------|
| **向量通道** | Milvus ANN | 语义相似实体/Cluster 召回 |
| **图谱通道** | Neo4j Cypher + PPR 多跳 | 路径遍历、时序重建、溯源 |
| **上下文过滤** | 条件过滤 | tenant_id / session_id / 时间窗 |

### 10.2 PPR 多跳检索（核心机制）

借鉴 HippoRAG 的设计，检索不是直接搜索原始文档，而是：

```
查询向量 → ANN 命中入口 EntityNode → PPR 在 KG 上传播 → 命中相关 EventNode → 溯源 RawBlockRef
```

**为什么用 PPR（Personalized PageRank）**：普通 BFS/DFS 会无差别扩展，召回边界难控制。PPR 根据边权重和传播概率动态调整，自动平衡相关性与多样性。

### 10.3 结果融合

向量相似度（0-1）和 PPR score（无上限）量纲不同，采用 **RRF（Reciprocal Rank Fusion）** 基于排名融合，或归一化后按权重加权。

## 11. 遗忘机制

### 11.1 为什么需要遗忘

不加控制的长期记忆会面临：图谱噪声（过时记忆干扰检索）、存储成本无限增长、旧知识误导当前决策。遗忘不是删除，而是**有选择地降低旧记忆的可见性和权重**。

### 11.2 四种遗忘信号

| 信号 | 触发条件 | 举例 |
|------|---------|------|
| **时效度衰减** | 当前时间 > invalid_at，或距 valid_at > 365 天 | API Key 过期、版本号更新 |
| **低置信度过期** | confidence < 0.3 且持续 30 天无更新 | 抽取错误或噪声 |
| **显式覆盖** | 新事实与旧事实冲突，旧事实被 superseded | 用户从 pandas 切换到 polars |
| **访问频率衰减** | 长期未被检索也未在对话中出现 | 冷门实体逐步降权 |

### 11.3 三级执行策略

**软删除** → **归档** → **硬删除**

- 软删除：添加 `expired_at`，检索时默认过滤，支持人工恢复
- 归档：过期 90 天后迁移到冷存储（OSS），保留索引供按需恢复
- 硬删除：归档 1 年后，仅保留聚合统计信息

**豁免规则**：高频实体（usage_freq > 50）和被 SemanticCluster 引用的核心主题实体优先保留。

**与 SemanticCluster 的交互**：Cluster 内事件过期 < 50% 则保留 Cluster（标注"部分历史已归档"）；过期 ≥ 50% 则归档 Cluster 但保留其语义摘要。

## 12. 存储设计概要

### 12.1 数据规模估算

| 节点/边类型 | 量级（以 10 万 session/天为例） |
|------------|-------------------------------|
| EntityNode | 100-200 万 |
| EventNode | 50-100 万 |
| 关系边 | 100-300 万 |
| 日增量 | 约 10-20 万实体/事件 |
| 日增存储 | Neo4j ~5-10GB（含索引） |

### 12.2 生命周期策略

| 温度 | 存储位置 | 数据范围 |
|------|---------|---------|
| Hot | Neo4j / Milvus | 最近 90 天活跃数据 |
| Warm | OSS 标准存储 | 90 天 - 1 年 |
| Cold | OSS 归档存储 | 1 年 - 3 年 |
| Deleted | 仅保留聚合统计 | 3 年以上 |

### 12.3 多租户隔离

`tenant_id` 贯穿所有层：Neo4j 查询必须带 tenant_id 过滤，Milvus 按 tenant_id 分区。

## 13. 评估体系概要

### 13.1 分层评估

| 层次 | 关键指标 | 目标 |
|------|---------|------|
| 抽取层 | 实体 Precision > 0.80, Recall > 0.70 | 人工标注评估 |
| 去重层 | 归并准确率 > 0.75, 误合并率 < 0.05 | 人工审核 |
| 图谱层 | 入库成功率 > 0.98 | 自动化统计 |
| 检索层 | Recall@10 > 0.75, MRR > 0.60, 响应 < 500ms | 测试集 + 压测 |
| 语义层 | Cluster 主题准确性 > 0.70 | 人工评估 |

### 13.2 核心 Demo Query

| 查询 | 覆盖能力 |
|------|---------|
| "用户上次提到的 pandas 问题是什么？" | 实体查询 + 时间线 |
| "从 pandas 到 read_excel 的路径？" | 路径查询 |
| "和'数据读取'相关的历史？" | 语义联想（SemanticCluster） |
| "sess_xxx 中问题怎么解决的？" | 时间线重建（PRECEDES 链） |
| "'那个库'指的是什么？" | 跨会话指代解析 |

## 14. 风险与优先级

### 14.1 实施优先级

| 优先级 | 内容 |
|--------|------|
| **P0 不可妥协** | Raw Block 标准化、EntityNode / EventNode 基础模型、Neo4j 写入与溯源 |
| **P1 核心能力** | LLM 抽取 pipeline、实体去重、基础检索接口 |
| **P2 增强能力** | Milvus 向量召回、SemanticCluster 语义固化、PPR 多跳检索 |
| **P3 高级能力** | 完整遗忘机制、Agentic Sufficiency Loop、社区发现 |

### 14.2 关键风险

| 风险 | 缓解措施 |
|------|---------|
| LLM 输出不稳定 | 结构化解析失败 fallback + 完善错误处理 |
| 实体去重误合并 | 保守阈值 + 归并日志 + 人工审核 |
| 时序边错误 | 时间置信度分级，低置信度不建边 |
| 中文 Encoder 不可用 | 已验证小 LLM 路径可行，GLiNER 退居 fallback |

### 14.3 降级预案

| 场景 | 降级策略 |
|------|---------|
| LLM 服务不可用 | 切换到规则抽取（预定义工具名白名单） |
| Neo4j 写入延迟 | 异步队列缓冲，写入降级为批量模式 |
| 检索超时 | 返回向量召回结果，跳过图遍历 |
