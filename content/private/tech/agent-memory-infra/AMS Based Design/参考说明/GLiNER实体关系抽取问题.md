## 二、为什么中文会崩得这么彻底？

### 原因 1：训练数据的严重偏斜

GLiNER 的核心训练数据是：
- CoNLL-2003（英文新闻）
- OntoNotes（英文）
- FewNERD（英文）
- WNUT17（英文社交媒体）
- 少量"多语言"数据作为点缀

这些模型的"multilingual"能力，本质上是在**英文为主的海量数据**上训练后，用少量其他语言做了**迁移学习**。中文在训练集中的比例可能不到 5%，导致模型对中文的 token 边界、语义模式极其不敏感。

### 原因 2：中文分词与英文 NER 的架构错位

GLiNER 是**span-based**模型——它在英文 token 序列上预测起始/结束位置。英文有空格和清晰词边界：
```
"Book a flight from Shanghai to Beijing"
→ [Book] [a] [flight] [from] [Shanghai] [to] [Beijing]
```

中文没有空格，语义单元是字或词：
```
"上海今天天气怎么样"
→ [上] [海] [今] [天] [天] [气] [怎] [么] [样]
```

如果模型没有在海量中文数据上学会**中文字词边界的隐式切分**，它就无法正确预测 span。结果就是：
- 要么把整句话都标为一个实体（"上海今天天气怎么样" = City）
- 要么完全放弃（0 hits）

### 原因 3：`modern-gliner-bi-base` 的 bi-encoder 架构对中文更灾难

`modern-gliner-bi-base` 使用的是**bi-encoder**架构（实体标签和文本分别编码再交互），而 `gliner_multi-v2.1` 使用的是**cross-encoder**架构。

Bi-encoder 的优点是速度快，但缺点是对**细粒度边界定位**更粗糙——它需要分别学习"文本表示"和"标签表示"的对齐关系。对于训练数据稀缺的中文，这种对齐几乎没学会。

这就是为什么：
- `gliner_multi`（cross-encoder）中文还能"勉强抽到东西"（虽然整句都错）
- `modern-gliner-bi-base`（bi-encoder）中文直接**全军覆没**

### 原因 4：标签集的语义迁移失败

你用的标签 `City`、`Person`、`Transport`、`Date` 是**英文世界定义的实体类型**。这些概念在中文语境下的迁移并不自然：

- "上海"在中文里可能是一个城市名，但模型没见过足够的"上海=City"中文样本
- "我有10万闲钱"被标为 Person，说明模型把"我"或者整句话误判为了人物描述——这是**典型的英文训练偏差**（英文中"I have..."的主语位置常出现人名）

`gliner-relex-multi` 在英文航班句子上能完美抽取 `Shanghai`、`Beijing`、`flight`、`tomorrow morning`，但在中文理财句子上**0 hits**——这直接证明了模型不是"不懂理财"，而是**"不懂中文"**。

## 四、务实的工程路线建议

### 路线 A：接受现实，中文场景以 LLM 为主（推荐）

既然实测已经证明 GLiNER 在中文上不可依赖，**不要硬上混合架构的"理想形态"**。务实做法是：

```
Layer 1（GLiNER）：
  - 仅用于已知高频英文工具名的快速召回（如 pandas, read_excel, Kafka）
  - 对中文 block 直接跳过，或只作为可选加速层

Layer 2（规则）：
  - Trace 日志用规则映射（这部分不受影响）
  - 中文会话的时间解析用规则层

Layer 3（LLM）：
  - 承担 90%+ 的中文实体抽取、全部的关系/事件抽取
  - Prompt 不依赖 Layer 1 结果，直接全量抽取
```

虽然成本更高，但**准确率是第一位的**。在记忆系统里，"抽取错误"比"抽取慢"的代价大得多。

### 路线 B：尝试中文优化的替代模型

与其在 GLiNER 上死磕，不如测试以下模型：

| 模型 | 优势 | 延迟 |
|------|------|------|
| **Qwen2.5-7B-Instruct** | 中文理解极强，7B 可本地部署 | ~100-300ms |
| **GLM-4-9B-Chat** | 中文抽取任务 SOTA 级 | ~100-300ms |
| **DeepSeek-V2.5** (API) | 中文代码+对话都很强 | API 调用 |
| **GPT-4o-mini** (API) | 多语言平衡，抽取稳定性高 | ~500ms |

这些模型虽然比 GLiNER 慢 10-50 倍，但比 GPT-4 快得多，且**在中文上的抽取质量远超 GLiNER**。

### 路线 C：微调 GLiNER（不推荐作为短期方案）

虽然理论上可以微调，但：
- 需要 500-2000 条高质量中文标注
- 需要覆盖对话、天气、理财、机票等多样领域
- `modern-gliner-bi-base` 的 bi-encoder 架构对中文极度不友好，微调 ROI 很低
- 即使微调了，指代消解仍然做不了

**结论**：如果团队有充足的 NLP 工程资源，半年后可能看到效果；但如果是现在就要跑通 pipeline，**不要选这条路**。

# 补充
## 一、为什么 GLiNER 在中文上全军覆没？（根本原因）

在推荐替代方案前，先明确问题根源：

| 问题 | 说明 |
|------|------|
| **训练数据** | GLiNER 家族以英文为主（CoNLL、OntoNotes、FewNERD），中文占比可能不足 5% |
| **架构适配** | GLiNER 是 **span-based** 模型，依赖清晰的词边界。中文无空格分词，span 定位天然困难 |
| **标签迁移** | `City`、`Person`、`Transport` 等标签是英文世界的概念映射，中文语境下迁移失败 |
| **Bi-encoder 灾难** | `modern-gliner-bi-base` 的 bi-encoder 架构对训练数据稀缺的语言极度不友好 |

这就是为什么：
- 英文句子 `Book a flight from Shanghai to Beijing` → `gliner-relex-multi` **完美命中**
- 中文句子 `上海今天天气怎么样` → 被标为整句 `City`，或 **0 hits**

## 二、Bert/GLiNER 类替代方案调研

### 方案 1：百度 UIE 系列（最推荐的中文专用方案）

**UIE（Universal Information Extraction）** 是百度基于 **ERNIE 3.0** 专门为中文信息抽取设计的统一框架。它不是 NER 模型，而是**支持实体抽取、关系抽取、事件抽取的统一模型**。

#### 模型族谱

| 模型 | 基座 | 参数量 | 特点 | 适用场景 |
|------|------|--------|------|---------|
| `uie-nano` | ERNIE 3.0 Tiny | ~20-40M | 极致轻量，CPU 友好 | 边缘设备、超大规模吞吐 |
| `uie-base` | ERNIE 3.0 Base | **118M** | 速度和精度的平衡点 | **推荐作为 Layer 1 主力** |
| `uie-large` | ERNIE 3.0 Large | ~354M | 精度更高，但延迟增加 | 对精度要求极高的场景 |
| `uie-m-large` | ERNIE 3.0 | ~354M | 多语言版本 | 中英混合场景 |
| `PP-UIE-0.5B` | 自研生成式 | 0.5B | 生成式信息抽取 | 可本地部署的轻量 LLM 替代 |
| `PP-UIE-7B` | 自研生成式 | 7B | 最强效果，但需 GPU | 效果优先，可本地部署 |

#### 关键优势

1. **专门为中文设计**：ERNIE 3.0 在中文预训练语料上训练，对中文词边界、语义模式理解远超 GLiNER
2. **零样本/少样本抽取**：通过 `schema` 定义标签，无需微调即可抽取自定义实体类型
3. **统一框架**：一个模型同时做 NER + 关系抽取 + 事件抽取，和 AMS 的 Layer 1+2+3 架构天然契合

#### 实测参考

PaddleNLP 官方示例中，`uie-nano` 对中文句子的抽取效果：

```python
from paddlenlp import Taskflow

schema = ['时间', '选手', '赛事名称']
ie = Taskflow('information_extraction', schema=schema, model="uie-nano")
ie("2月8日上午北京冬奥会自由式滑雪女子大跳台决赛中中国选手谷爱凌以188.25分获得金牌！")

# 输出：
# [{'时间': [{'text': '2月8日上午', 'probability': 0.65}],
#   '赛事名称': [{'text': '北京冬奥会自由式滑雪女子大跳台决赛', 'probability': 0.49}],
#   '选手': [{'text': '谷爱凌', 'probability': 0.98}]}]
```

注意：概率值看起来不高，但**边界识别是准确的**——"北京冬奥会..."被完整抽出，"谷爱凌"精准定位。这和 GLiNER 把"上海今天天气怎么样"整句标为 `City` 有本质区别。

#### 速度参考

- `uie-base` (118M)：CPU 上约 **10-30ms/条**，GPU 上 **2-5ms/条**
- `PP-UIE-7B`：batch=1 时 **~40ms/条**（TPS ~25），和 GLiNER 的延迟处于同一量级

### 方案 2：中文 BERT/RoBERTa 的 NER 微调版本

如果你只需要**纯 NER**（不需要关系抽取），以下模型可以直接用：

| 模型 | 基座 | 参数 | 标签集 | 来源 |
|------|------|------|--------|------|
| `ckiplab/bert-base-chinese-ner` | BERT-base-chinese | 102M | 人名/地名/组织/时间等经典 NER | 台湾中研院 |
| `uer/roberta-base-finetuned-cluener2020-chinese` | RoBERTa-wwm-ext | 102M | 基于 CLUENER 的 10 类标签 | 追一科技/UER |
| `shibing624/macbert4cner-base-chinese` | MacBERT-base | 102M | 中文命名实体识别 | 社区微调 |

**缺点**：
- 标签集是**固定的**（CLUENER 的标签：地址、书名、公司、游戏、政府、电影、姓名、组织、职位、景点），和 AMS 的 `TOOL/CONCEPT/RESOURCE` 不完全匹配
- 只做 NER，**不支持关系抽取**
- 需要额外微调才能适应自定义标签

**优点**：
- HuggingFace 生态可直接用 `transformers` 加载
- 不需要引入 PaddlePaddle 框架

### 方案 3：自研微调一个小模型

如果你有 500-2000 条标注数据，可以在以下基座上微调：

| 基座 | 参数 | 建议 |
|------|------|------|
| `bert-base-chinese` | 102M | 最稳定，社区资料最多 |
| `chinese-roberta-wwm-ext` | 102M | 中文效果略好于 BERT |
| `macbert-base-chinese` | 102M | 纠正了 BERT 预训练中的字掩码问题 |
| `ernie-3.0-base-zh` | 118M | 中文理解最强，但需 PaddleNLP |

**但这条路的问题是**：你需要的不是"标准 NER"，而是**自定义标签 + 关系抽取 + 事件抽取**。这种复杂任务用 UIE 的零样本能力直接做，比从头微调 BERT 更快。

**中文信息抽取的正确工具是 UIE 或 LLM，不是 GLiNER。**
