

# EventNode 类型定义方法论思考

## 1. 问题定义

在 AMS 的 Temporal KG 中，EventNode 是情景记忆的时序单元。每个 EventNode 需要一个 `event_type` 字段来标识事件类型。与 EntityNode 的类型定义一样，这个类型体系的设计影响三件事：

1. **事件分类模型的准确率**——事件类型分类可由 BERT 类模型做句子级分类（Layer 1），类型数量和边界清晰度直接影响分类效果
2. **时序链和桥接边的构建规则**——PRECEDES 边的置信度、Session-Trace 桥接边的匹配规则都依赖 event_type 做前置过滤
3. **检索时的策略路由**——时间线查询、因果追溯、语义联想对不同类型的事件有不同的召回逻辑

本文记录事件类型设计的方法论依据、与技术选型的关系，以及识别出的待验证风险。

## 2. 与实体类型的根本差异

在进入方法论之前，需要先明确 EventNode 和 EntityNode 在本质上的不同，因为这个差异决定了两者的类型定义不能用同一套逻辑。

| 维度 | EntityNode | EventNode |
|------|-----------|-----------|
| **本质** | 概念/事物（what） | 一次发生（what happened） |
| **唯一性** | 同一实体可能被多次提及，需要归一 | 每次发生都是独一无二的，天然唯一 |
| **去重** | 必须（"pandas" = "pd" = "那个库"） | 不需要（即使描述相似，也是不同次发生） |
| **类型的含义** | "Agent 会怎么用这个实体" | "这个事件在任务流程中扮演什么角色" |

EntityNode 的类型定义遵循"交互语义驱动"——类型是 Agent 与实体交互的接口协议。EventNode 的类型定义遵循的是另一个逻辑：**事件在任务流程中的功能角色**。

两者的共同上层原则是一致的：

> **类型 = 在系统中的功能角色，而非本质属性。**

## 3. 我们的方法论：双来源功能角色分类

### 3.1 为什么事件类型按来源分成两组

当前的 7 类事件类型不是一个扁平列表，而是按 Session / Trace 两条来源链路分成了两组：

| 来源 | 事件类型 | 数量 |
|------|---------|------|
| Session（对话） | user_request, decision, problem, solution | 4 类 |
| Trace（执行日志） | tool_use, tool_result, artifact_create | 3 类 |

这个分组不是随意的。Session 和 Trace 观察的是同一次交互的两个视角（第1章 1.1节），它们产生的事件在语义性质上有本质差异：

- **Session 事件**是对话行为——"用户说了什么"、"做了什么决定"
- **Trace 事件**是执行状态——"系统调了什么工具"、"返回了什么结果"

两组事件的分类依据来自不同的理论传统。

### 3.2 Session 侧 4 类：来自对话行为理论

Session 侧的 4 类事件对应的是**对话行为理论（Dialogue Act Theory）**中任务型对话的核心行为类型。

对话行为理论的核心思想是：一句话不仅有语义内容，还有**言语功能（illocutionary force）**——它是在"请求"、"报告问题"、"做决策"还是"提供方案"。这个理论从 Searle 的言语行为理论（Speech Acts, 1969）发展而来，后续在 DAMSL 标注体系和 ISO 24617-2（对话行为标注国际标准）中被形式化。

我们的 4 类与对话行为理论的映射：

| 我们的类型 | 对话行为理论中的对应 | 学术来源 | 功能 |
|-----------|-------------------|---------|------|
| `user_request` | Request / Ask（请求类） | Searle 的言语行为分类 | 发起任务 |
| `problem` | Inform-Negative / Report-Problem | ISO 24617-2 | 报告障碍 |
| `decision` | Commit / Accept（承诺/决策类） | DAMSL 标注体系 | 确定方向 |
| `solution` | Inform-Positive / Answer | ISO 24617-2 | 解决问题 |

这 4 类恰好覆盖了一个任务闭环的核心阶段：

```
user_request（提需求）→ problem（遇障碍）→ decision（做决策）→ solution（给方案）
```

不是所有任务都会完整经历这 4 个阶段（有些需求直接就有方案，不经过 problem），但这 4 个类型足以描述 Agent 对话中观察到的绝大多数事件。

### 3.3 Trace 侧 3 类：来自执行状态机

Trace 侧的 3 类事件对应的是**工具调用的执行生命周期**，理论来源是 OpenTelemetry 的 Span 模型。

一个工具调用（Span）有明确的生命周期：**发起 → 完成 → 可能产出副产物**。我们的 3 类对应了这个生命周期的三个阶段：

| 我们的类型 | 执行状态机中的对应 | 来源参考 | 功能 |
|-----------|----------------|---------|------|
| `tool_use` | Action / Invocation（动作触发） | OTEL Span Start | 记录"调了什么" |
| `tool_result` | Result / Completion（动作完成） | OTEL Span Status | 记录"结果如何" |
| `artifact_create` | Side Effect / Output（副产物） | 构建系统 artifact 概念 | 记录"产出了什么" |

这个生命周期模型比 Session 侧更清晰——tool_use 和 tool_result 是严格的配对关系（有调用就有返回），artifact_create 是可选的（不是每次调用都有产出）。

### 3.4 两组之间的桥接

两组事件虽然来自不同的理论传统，但它们描述的是同一次交互。在图谱中通过桥接边连接：

```
user_request（用户提需求）
    → REQUEST_LEADS_TO → tool_use（系统调工具）
                              → tool_result（工具返回）
                                    → EVIDENCES → solution（问题解决）
```

桥接边的匹配规则依赖 event_type 做过滤：只有 Session 类型的事件和 Trace 类型的事件之间才创建桥接边，同组事件之间不创建桥接边（它们用 PRECEDES 时序边连接）。

## 4. 技术选型约束

### 4.1 事件类型分类的执行层

根据混合抽取架构的设计（详见《BERT或GLiNER替代实体关系抽取》），事件抽取是"混合替换"模式：

```
Raw Block
  → [GLiNER/BERT] 事件触发词检测 + 类型分类    (Layer 1, ~15ms)
  → [规则/duckling] 时间表达式解析             (Layer 2, ~1ms)
  → [LLM] 复杂推理部分                        (Layer 3, ~1-2s)
      - 相对时间 → 绝对时间转换
      - participants 绑定
      - confidence 评估
      - 跨句因果推断
```

其中 **event_type 分类** 在 Layer 1 由 BERT 类模型做句子级分类。设计文档的评估是："事件类型分类（7种）✅ 可以做分类，句子级分类任务，BERT 类很擅长。"

### 4.2 封闭集约束

与实体类型类似，BERT 句子级分类器是封闭集操作——你定义几个类别，模型只能从中选。所以 **7 类事件类型也是封闭集**。

但与实体类型的约束模式有一个关键区别：

| 维度 | 实体类型 | 事件类型 |
|------|---------|---------|
| **Layer 1** | GLiNER 封闭集分类 | BERT 封闭集分类 |
| **LLM 兜底** | 无（Layer 1 是最终结果） | 有（Layer 3 可以修正） |
| **封闭程度** | 硬封闭 | 软封闭 |

实体类型是"硬封闭"——GLiNER 的输出就是最终类型，没有 LLM 修正通道。事件类型是"软封闭"——BERT 做初分类，复杂场景下 LLM 可以修正（比如判断一段话到底是 problem 还是 user_request）。

但即使有 LLM 修正通道，修正也应该在同一个 7 类封闭集内进行，而不是发明新类型。原因是：

1. **PRECEDES 边的构建规则**依赖已知的 event_type 集合
2. **桥接边的匹配规则**按 Session/Trace 来源过滤，新类型如果来源不明确会打破匹配逻辑
3. **检索层的策略路由**是按 event_type 硬编码的，新类型无法被现有路由识别

### 4.3 7 类在 BERT 分类器的性能预期

与 GLiNER 对实体类型 label 的效果差异类似，BERT 句子级分类器对 7 类事件类型的预期效果也不均匀：

| event_type | 预期效果 | 原因 |
|-----------|---------|------|
| `tool_use` | ⭐⭐⭐⭐⭐ | Trace 日志中有明确的结构化标识（tool_name 字段），几乎不需要语义理解 |
| `tool_result` | ⭐⭐⭐⭐⭐ | 同上，status 字段直接标识 |
| `artifact_create` | ⭐⭐⭐⭐ | 通常有明确的输出标识（文件名、路径） |
| `user_request` | ⭐⭐⭐ | 疑问句、祈使句模式相对明确，但与 problem 可能混淆 |
| `problem` | ⭐⭐⭐ | "报错"、"失败"等关键词有辨识度，但与 user_request 的隐含抱怨可能混淆 |
| `solution` | ⭐⭐ | 需要理解"问题被解决了"的语义，不是简单的关键词匹配 |
| `decision` | ⭐⭐ | 最难——"用户做了决定"和"用户提了需求"在表面形式上非常相似 |

**关键观察**：Trace 侧 3 类效果预期远好于 Session 侧 4 类。这是因为 Trace 日志本身就是结构化的（有 tool_name、status、output 等字段），类型判断几乎可以用规则完成。真正的分类难度集中在 Session 侧——自然语言对话的言语功能识别本来就是 NLP 的经典难题。

## 5. 与实体类型方法论的对比

| 维度 | 实体类型（6 类） | 事件类型（7 类） |
|------|--------------|--------------|
| **方法论** | 交互语义驱动 | 双来源功能角色分类 |
| **理论根基** | 语义角色理论（FrameNet） | 对话行为理论 + OTEL 执行状态机 |
| **分类轴** | "Agent 怎么用这个实体" | "事件在任务流程中的功能角色" |
| **选型约束** | GLiNER 硬封闭 | BERT 初分类 + LLM 修正，软封闭 |
| **主要风险** | 领域特定 label 效果差 | Session 侧 4 类之间边界模糊 |
| **归一化** | 必须（同一实体多次出现） | 不需要（每次发生天然唯一） |

## 6. 优势总结

**1. 有明确的理论根基。** Session 侧来自对话行为理论，Trace 侧来自 OTEL 执行状态机。两个理论传统在各自的领域都经过了充分验证，不是拍脑袋设计的。

**2. 按来源分组降低了分类难度。** 在实际处理中，一个 Raw Block 的 source_type 是已知的（session 或 agent_trace）。分类器不需要在 7 个类中选，而是根据来源缩小到 4 个（Session）或 3 个（Trace）。这对 BERT 分类器的准确率有显著帮助。

**3. 覆盖了任务型对话的核心闭环。** "请求→问题→决策→方案"加上"调用→结果→产出"，两个闭环的组合覆盖了 Agent 交互中绝大多数有记忆价值的事件。

**4. Trace 侧几乎可以用规则完成。** tool_use / tool_result / artifact_create 的分类在结构化 Trace 日志中是确定性的，不依赖 NLP 模型，这让 Trace 侧的事件抽取又快又准。

## 7. 待验证的风险

### 7.1 Session 侧 4 类之间的边界模糊（最高风险）

这是事件类型体系中最大的风险，严重度高于实体类型中 CONCEPT/RESOURCE 的边界问题。

**原因**：实体类型的模糊主要发生在 CONCEPT/RESOURCE 之间（一对关系），而事件类型的模糊可能发生在 Session 侧 4 类的**任意两两组合**之间。一句话可能同时包含多种言语功能。

**典型模糊案例**：

| 用户说的话 | 可能的类型 | 模糊原因 |
|-----------|----------|---------|
| "pandas 读 CSV 报错了，我觉得应该用 dtype 参数" | problem + decision | 一句话包含报告问题和做出决策 |
| "帮我把这个 Excel 转成 CSV" | user_request 还是 decision？ | 既是请求也是决策 |
| "试了你的方案，还是不行" | problem 还是 user_request？ | 既是报告问题也是隐含的再次请求 |
| "好的，那就用 polars 吧" | decision 还是 solution？ | 既是做出决策也是确认方案 |

**验证方法**：
- 在标注实验中记录 Session 侧事件的分类犹豫率
- 如果 user_request vs problem 或 decision vs solution 的混淆率 > 30%，考虑合并
- 极端方案：Session 侧简化为 2 类（`request` = user_request + problem，`response` = decision + solution），只保留"发起"和"回应"的区分

### 7.2 "纯信息传递"事件的缺失

当前 7 类覆盖了"请求→问题→决策→方案"闭环，但缺少一类：用户提供背景信息但不带任何请求/问题/决策意图的情况。

**示例**：
- "顺便说一下，我们的数据是按天分区的"
- "这个项目用的是 Python 3.10"
- "我们公司不允许用外部 API"

这些信息对后续记忆检索可能很重要（它们包含实体和约束），但不符合当前任何事件类型。当前方案中，这类话可能被：
- LLM 跳过不抽取（因为不符合任何事件类型定义）
- 强行归到 user_request（语义失真——它不是在请求什么）

**缓解方案**：
- 方案 A：增加 `inform` 类型（纯信息传递），从 7 类扩展到 8 类
- 方案 B：不增加事件类型，依赖实体/关系抽取来捕获这些信息（这些话里的实体和事实仍然会被 Prompt 2a 和 2c 抽取）
- 方案 C：先按方案 B 运行，统计被跳过的 Block 中有多少包含重要信息，数据说话

推荐方案 C。当前阶段不急于扩展类型，先验证"不抽事件但抽实体/关系"是否足够覆盖这些信息。

### 7.3 按来源硬分类型的边界情况

当前设计是 Session 事件只能是 4 类之一，Trace 事件只能是 3 类之一。但有些 Agent 框架会在对话消息流中直接展示工具调用过程（把 Trace 信息嵌入到 Session 中）。

**示例**：Session 消息流中出现 `assistant: [调用 python_executor] read_csv("data.csv") → 成功`

这条消息的 source_type 是 session，但内容是工具调用——应该归为 user_request / decision / problem / solution 中的哪个？还是应该识别为 tool_use？

**处理策略**：
- 在输入适配层（Stage 0）做预处理：如果 Session 消息内容匹配工具调用模式（正则或结构化标识），将其拆分为两个 Raw Block——一个 session 类型（用户意图部分），一个 agent_trace 类型（工具调用部分）
- 不在事件类型层面解决这个问题，而是在输入层确保 source_type 的准确性

### 7.4 decision 和 solution 的实际区分价值

从检索层来看，decision（"决定用 dtype 参数"）和 solution（"问题通过 dtype 参数解决了"）在下游的使用方式非常相似——都是"找到了处理办法"。它们的区别主要在于时序位置：decision 在执行之前，solution 在执行之后。

**问题**：这个区分在检索时是否真的有价值？如果用户查"上次那个问题怎么解决的"，decision 和 solution 都应该被召回。

**验证方法**：在 demo query 用例中测试——把 decision 和 solution 合并为一类 `resolution` 后，检索质量是否有可感知的下降。如果没有，7 类可以简化为 6 类。

## 8. 改进建议

### 8.1 标注实验的重点

与实体类型一样，用 20-30 条真实 Agent 对话做标注实验。但事件类型的标注需要特别关注：

- **一句话包含多个事件类型的频率**——如果 > 30%，说明"一个 Block 可以抽出多个 EventNode"的设计是必要的
- **Session 侧 4 类的混淆矩阵**——哪两类之间混淆最严重
- **被跳过的 Block 比例**——有多少 Block 不符合任何事件类型但包含有价值的信息

### 8.2 分层验证策略

鉴于 Trace 侧和 Session 侧的分类难度差异悬殊，建议分开验证：

| 阶段 | 验证内容 | 预期结果 |
|------|---------|---------|
| 第一步 | Trace 侧 3 类用规则分类 | 准确率 > 95%（结构化数据，几乎确定性） |
| 第二步 | Session 侧 4 类用 BERT 分类 | 准确率目标 > 75%，重点看混淆矩阵 |
| 第三步 | 混淆严重的类对，评估是否合并 | 如 decision/solution 合并后检索质量无损，则简化 |

### 8.3 与实体类型的联动调整

如果实体类型中的 ACTION 最终被移除（因为与 EventNode 职责重叠），事件类型不需要相应变更——EventNode 本身就承载了"动作"的语义，ACTION 实体类型的移除反而消除了冗余。

但如果事件类型中的 decision/solution 被合并，需要同步调整桥接边的匹配规则——当前 `ATTEMPTS_TO_SOLVE` 边专门连接执行事件和 problem/solution 事件，合并后需要更新这条规则。
