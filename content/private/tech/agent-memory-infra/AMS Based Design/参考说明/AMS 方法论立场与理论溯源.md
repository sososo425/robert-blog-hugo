# AMS 方法论立场与理论溯源

> 本文整理自设计过程中的讨论，澄清 AMS 类型体系设计的方法论立场，以及背后涉及的理论概念。
> 日期：2026-04-12
> 关联文档：《EntityNode 类型定义方法论思考》、《Temporal-KG 边类型定义的方法论思考 v2.0》

## 1. 我们的方法论立场：一句话

**工程驱动，理论可溯源，但不被理论绑架。**

AMS 的类型体系设计（EntityNode 的 6 种实体类型、关系边的 6+1 种类型、以及 B-E 四类固定边）是工程实践——怎么有效怎么来，首要目标是实现可用的系统。背后的理论提供语义原型和设计参考，需要时能回去查，日常不背着它走。

| 我们实际做的                      | 背后能映射到的理论                     | 但我们没做的             |
| --------------------------- | ----------------------------- | ------------------ |
| 6 个实体类型，GLiNER 能识别就行        | Schema.org 800+ 类型、SUMO 的实体层次 | 没有去追求分类的逻辑完备性      |
| 6 种核心关系谓词（`causes`、`uses`…） | SUMO 的形式化关系定义、FrameNet 的语义框架  | 没有引入公理系统或框架标注体系    |
| 时间衰减 + 强化机制                 | 认知科学的记忆衰减理论                   | 没有去建认知模型           |
| LLM 做关系抽取                   | NLP 的语义角色标注（SRL）传统            | 没有用传统 NLP pipeline |

## 2. "本体论"概念澄清

### 2.1 本体论的概念流变

本体论（Ontology）是一个被反复"回炉利用"的概念，每一代人重新发现"我们需要给世界分类"这件事，然后给它起个名字：

- **亚里士多德（公元前 4 世纪）**——"存在之为存在"的分类：实体、性质、关系、数量……这是哲学意义上的本体论。
- **Tom Gruber (1993)**——计算机科学借用了这个概念，给出工程化定义：*"An ontology is a formal, explicit specification of a shared conceptualization"*。从此"本体论"进入了 IT 领域。
- **语义网时代（2000s-2010s）**——OWL、RDFS、Protégé 工具，学术圈搞了很多上层本体（SUMO、DOLCE、BFO）。
- **Palantir Foundry（2020s）**——把"Ontology"包装成企业数据建模的核心概念，营销驱动的术语复兴。本质上是"企业数据模型 + 权限 + 操作绑定"，和亚里士多德的哲学关系很远。

核心思想一直没变——**给世界分类**。但外壳换了好几次。

### 2.2 Schema.org 和 DBpedia 不是本体论

它们是**借用了本体论建模思想的工程产物**，不是哲学产物：

- **Schema.org**——Google、微软、Yahoo 2011 年联合搞的一套**结构化标记词汇表**。目的很实用：让网页能被搜索引擎理解。它定义了 800+ 类型（`Person`、`Organization`、`Event`、`MedicalCondition`…）和大量属性。本质上是给 SEO 用的。
- **DBpedia**——从 Wikipedia 的 infobox 里**自动抽取**出来的结构化知识库。它有 700+ 类型的分类体系（从 Wikipedia 的分类树映射来的）。本质上是一个知识图谱数据集。

它们借用了本体论的建模思想（类型层次、属性约束、is-a 关系），但本身是工程产物。就像用面向对象编程不代表在研究柏拉图的"理型"。

## 3. AMS 设计中涉及的理论概念

### 3.1 Upper Ontology（上层本体）

如果要给世界上所有的东西分类，最顶上那几个类别是什么？这就是 Upper Ontology 干的事——定义**最抽象、最通用**的分类，不属于任何具体领域。

```
典型顶层分类：

Entity（实体）
├── Physical（物理的）
│   ├── Object（物体）
│   └── Process（过程）
└── Abstract（抽象的）
    ├── Quantity（数量）
    ├── Relation（关系）
    └── Attribute（属性）
```

可以理解为**人类认知的最大公约数**。学术上搞了好几个（SUMO、DOLCE、BFO），互相不兼容，也没有谁真正统一了。理想很好，现实比较骨感。

### 3.2 SUMO（Suggested Upper Merged Ontology）

直译：**建议的上层合并本体**。2000 年前后由 IEEE 标准化工作组启动，Adam Pease 主导，试图把当时已有的几个 Upper Ontology 合并成一个。定义了约 25,000 个概念和 80,000 条公理。

AMS 边类型文档里提到的 `causes`、`uses`、`enables` 这些关系，SUMO 里都有形式化定义。例如 SUMO 对 `causes` 的定义（简化）：如果 A causes B，那么 A 和 B 都得是 Process，且 A 在时间上早于 B。

**和 AMS 的关系**：我们把 `causes`、`uses` 这些谓词拿来用了，但没有照搬 SUMO 的形式化体系——只是借了几个语义上有共识的词。

**现状**：学术界有一定影响，工业界基本没人直接用。太重了。

### 3.3 FrameNet

这个和前两个**完全不是一个领域**——它来自**语言学**，不是知识工程。

核心思想：人类理解语言靠的是"框架"（Frame）。比如听到"买"这个词，脑子里自动激活一个"商业交易框架"，包含 Buyer（买方）、Seller（卖方）、Goods（商品）、Money（货款）等角色。

FrameNet 是 UC Berkeley 的语言学家 Charles Fillmore 1997 年启动的项目，手工标注了 1,200+ 个语义框架和 200,000+ 标注句子。框架之间也有关系：Inheritance（继承）、Causative_of（致使）、Using（使用）、Subframe（子框架）。

**和 AMS 的关系**：
- EntityNode 文档借鉴了 FrameNet 的 Frame Element 概念（语义角色：Agent、Instrument、Patient）来定义实体类型。
- 边类型文档借鉴了 FrameNet 对关系的语义分类（框架间的 Uses、Causative_of 关系），但没有引入框架标注体系。

**现状**：NLP 领域广泛引用，但直接基于 FrameNet 做系统的不多。更多是启发了后续的**语义角色标注**（SRL）研究。

### 3.4 三者的关系

```
        来自哲学/知识工程                来自语言学
        ─────────────────              ────────────
        
        Upper Ontology                 FrameNet
        (抽象理念：给世界分类)            (人怎么理解语言)
              │                              │
              ▼                              │
           SUMO                              │
     (一个具体实现：                          │
      25000概念+公理)                        │
              │                              │
              └──────────┬───────────────────┘
                         │
                         ▼
               AMS 从两边各借了一点
               语义原型（但没照搬任何一个）
```

## 4. 边类型文档中"知识图谱关系本体论"的修正

原文档第 44 行使用了"知识图谱关系本体论"这个说法。经讨论确认：

- **这不是行业标准术语**，是文档自己造的组合词。
- 行业里有共识的相关概念包括：Relation Ontology（RO，特指生物医学领域 OBO Foundry 的那个）、Upper Ontology（SUMO/DOLCE）、Knowledge Graph Schema（知识图谱的 schema 层）。但不存在一个叫"知识图谱关系本体论"的学科。
- 文档想表达的意思是：边类型的语义原型参考了知识图谱领域中**对关系类型的形式化分类传统**（即 SUMO 的 `causes/uses`、FrameNet 的语义框架、Schema.org 的 Action 模型这些）。

已修正为 **"KG 关系类型形式化传统"**，避免让人误以为存在一个成体系的学科。

| ----------- | ------------------------------------------------------------------------------------------ | --------------------------------------------- |
| **对本体论的态度** | 明确拒绝引入（第 2 节标题就是"我们没有选择的路"）                                                                | 承认理论渊源，但不照搬（修正后明确为"参考坐标系，不是方法论"）              |

## 6. 总结

AMS 的整个类型体系——实体类型、事件类型、5 大类 16 种边类型——背后的方法论立场是统一的：

1. **我们是工程实践**，首要目标是造一个能跑的系统，不是构建一套逻辑自洽的本体论。
2. **理论是参考坐标系**，不是设计约束。SUMO 告诉我 `causes` 这个谓词有共识定义，FrameNet 告诉我语义角色怎么分，Schema.org 告诉我 Web 实体怎么标记——我各取所需。
3. **不被理论绑架**。我们不追求分类的逻辑完备性，不引入公理系统，不背负几千个类型的维护成本。6 个实体类型、6 种关系谓词，够用就行。
4. **可溯源但不可依赖**。任何一个设计决策，都能追溯到某个理论传统的语义原型，但如果那个理论明天被推翻了，我们的系统不会受影响——因为我们依赖的是工程效果，不是理论正确性。
