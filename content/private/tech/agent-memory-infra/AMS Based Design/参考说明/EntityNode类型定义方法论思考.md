
# EntityNode类型定义方法论思考

## 1. 问题定义

在 AMS 的 Temporal KG 中，EntityNode 是语义记忆的基本单元。每个 EntityNode 需要一个 `entity_type` 字段来标识类型。这个类型体系的设计直接影响三件事：

1. **抽取模型的分类能力**——实体抽取层采用 GLiNER（BERT 类判别式模型），类型定义的数量和命名直接影响模型的分类准确率
2. **检索时的策略选择**——不同类型的实体在检索时需要不同的召回和排序策略
3. **图谱的长期可维护性**——类型体系一旦确定，后续变更成本很高

本文记录我们在设计这套类型体系时的思考过程、遵循的方法论，以及经过 review 后识别出的待验证风险。

## 2. 我们没有选择的路：传统本体论

最直觉的做法是参考传统知识图谱的本体论（Ontology）设计，比如 Schema.org、DBpedia Ontology、SUMO 等。这些体系追求的是**逻辑完备性**——世界上所有的东西都能在分类树上找到位置。

我们没有走这条路，原因有三：

**第一，本体论的类型体系太庞大。** Schema.org 有 800+ 类型，DBpedia 有 700+ 类型。Agent 运行时产生的实体只涉及其中很小的一个子集（工具、文件、概念、人），引入完整的本体论是过度设计。

**第二，本体论的分类依据是"本质属性"，但 Agent 场景不需要本质属性。** 对 Agent 来说，pandas 是一个"Python 库"还是一个"开源项目"还是一个"软件工具"，并不重要。重要的是 Agent 检索到 pandas 之后会怎么用它——调用它、解释它、还是定位它的文件路径。

**第三，本体论的类型边界争论是无底洞。** "DataFrame 是工具还是概念？""data.csv 是资源还是制品？"这类问题在本体论框架下永远有争议，因为同一个东西在不同视角下确实属于不同类型。我们需要一个能终止争论的判断标准。

## 3. 我们的方法论：交互语义驱动

### 3.1 理论基础：语义角色理论

我们的类型设计在语言学上有一个隐含的理论根基——**语义角色（Semantic Roles）**。

在语言学的 FrameNet 和 PropBank 框架中，一个事件的参与者按照其扮演的语义角色来分类：

| 语义角色              | 定义          | 例句中的体现                      |
| ----------------- | ----------- | --------------------------- |
| Agent（施事）         | 有意志地发起动作的主体 | **用户**用 pandas 读取了 data.csv |
| Instrument（工具）    | 被用来完成动作的手段  | 用户用 **pandas** 读取了 data.csv |
| Patient/Theme（受事） | 动作作用的对象     | 用户用 pandas 读取了 **data.csv** |
| Location（场所）      | 动作发生的环境/范围  | 在 **Acme Corp** 的数据平台上操作    |

这个框架的核心洞察是：**同一个实体在不同事件中可能扮演不同的语义角色，但大多数实体有一个"最典型"的角色。** pandas 偶尔会被"提及"（受事），但它最典型的角色是"被调用"（工具）。

### 3.2 从语义角色到交互模式

语义角色理论告诉我们"实体在事件中扮演什么角色"，但它是句子级别的分析框架，不能直接用于图谱设计。我们需要把它投射到 Agent 的工程场景上。

投射的关键问题是：**Agent 检索到一个实体后，会以什么方式与之交互？**

这就是我们方法论的核心——**交互语义驱动（Interaction-Semantic Driven）**：

> **类型不是实体的本质属性，而是 Agent 与之交互的接口协议。**

语义角色提供了理论分类轴，交互模式提供了工程判断标准。两者的映射关系如下：

| 语义角色              | 投射后的交互模式                 | 对应 entity_type   |
| ----------------- | ------------------------ | ---------------- |
| Agent（施事）         | **归因交互**——"谁做的？谁说的？"     | `PERSON` / `ORG` |
| Instrument（工具）    | **调用执行**——"用什么做？怎么调用？"   | `TOOL`           |
| Patient/Theme（受事） | **定位访问**——"操作的是什么对象？在哪？" | `RESOURCE`       |
| 无直接对应             | **理解推理**——"这是什么概念？怎么理解？" | `CONCEPT`        |
| 无直接对应             | **追踪复盘**——"做了什么动作？"      | `ACTION`         |

其中 CONCEPT 和 ACTION 没有直接对应的经典语义角色，是根据 Agent 场景的实际需要补充的。CONCEPT 对应的是事件的"背景知识"（非参与者但需要理解），ACTION 对应的是事件本身的动作抽象。

### 3.3 最终的类型定义

基于上述推导，我们确定了 6 类实体类型：

| 类型         | 交互模式 | 典型实体                                | Agent 拿到后的典型行为  |
| ---------- | ---- | ----------------------------------- | --------------- |
| `TOOL`     | 调用执行 | pandas, read_excel, python_executor | 生成代码、调用工具、查询用法  |
| `CONCEPT`  | 理解推理 | dtype, CSV解析, 数据清洗                  | 解释概念、关联知识、辅助推理  |
| `RESOURCE` | 定位访问 | data.csv, output.xlsx, model_v2.pkl | 找路径、读内容、检查状态    |
| `PERSON`   | 归因交互 | 用户, Alice, agent_v2                 | 个性化响应、权限判断、偏好召回 |
| `ORG`      | 范围限定 | Acme Corp, DataPlatform             | 策略选择、规范约束、租户隔离  |
| `ACTION`   | 追踪复盘 | 读取Excel, 排查报错                       | 检索历史执行记录、复盘步骤   |

**控制在 6 类**既是设计选择，也是技术约束。实体抽取层采用 GLiNER（BERT 类判别式模型）而非生成式 LLM，GLiNER 的分类准确率随 label 数量增长而下降，在 5-10 个 labels 时表现最好。6 类正好在这个最优区间内。

## 4. Graphiti 的实体类型设计参考

Graphiti（getzep/graphiti）是本系统在 Temporal KG 设计上的核心参考项目。Graphiti 对实体类型的处理采用了一种更灵活的机制。

### 4.1 Graphiti 的多标签体系

Graphiti 的 EntityNode 使用 `labels: list[str]` 而非单一 `entity_type` 字段：

```python
EntityNode:
  uuid: "ent-zhangwei"
  name: "张伟"
  labels: ["Person", "Engineer", "Manager"]  # 多标签
  attributes: dict[str, Any]  # 自定义属性，由 Pydantic Schema 定义
```

这意味着一个实体可以同时持有多个类型标签——"张伟"既是 Person 又是 Engineer。

### 4.2 Graphiti 的类型传入机制

Graphiti 提供两种模式：

- **不传 `entity_types`**：所有实体归为通用 Entity 类型，LLM 自由抽取。开箱即用但分类粗糙。
- **传入 `entity_types`**：调用方用 Pydantic Model 定义类型（如 Person、Organization），Graphiti 内部自动把 dict key 按顺序映射为 `entity_type_id = 1, 2, 3...`，连同 docstring 描述一起拼入 Prompt 给 LLM 做分类。

### 4.3 我们的适配决策

我们选择了**封闭集单标签 `entity_type`**，原因是：

1. **技术选型约束**——实体抽取层采用 GLiNER（BERT 类判别式模型）而非生成式 LLM。GLiNER 本质上是封闭集序列标注器，调用时传入一个 labels 列表，模型只能从该列表中选择，不支持开放类型生成。封闭类型体系是模型能力的硬约束，而非仅仅是工程偏好。
2. **分类性能最优区间**——GLiNER 在 5-10 个 labels 时表现最好，6 类正好在最优区间内。超过 15-20 个 labels 后准确率会明显下降。
3. **Pipeline 类型空间一致性**——实体去重（Stage 3）和关系抽取（Prompt 2c，仍用 LLM）都依赖稳定的类型标签做前置过滤。封闭类型体系保证了各阶段类型空间的一致性，不会出现上游抽出了一个下游不认识的类型。
4. **简化下游逻辑**——检索时按单一类型路由策略，不需要处理多标签组合的排列爆炸。

但 Graphiti 的 `attributes` 设计（用 Pydantic Schema 定义自定义属性、由 LLM 自动填充）值得后续引入。当单一 `entity_type` 不够表达时，可以通过 attributes 补充结构化信息，而不需要新增类型。

### 4.4 封闭集 vs 开放集：与混合抽取架构的关系

我们的抽取 Pipeline 采用三层混合架构（详见《BERT或GLiNER替代实体关系抽取》）：

```
Layer 1: GLiNER          ~10-30ms    ~$0    封闭集分类
├── 实体抽取 (NER)
├── 实体类型分类
└── 事件触发词检测

Layer 2: 规则/轻量模型    ~5ms       ~$0    封闭集
├── 时间表达式解析
├── 停用词过滤
└── 预定义关系类型分类

Layer 3: LLM             ~1-2s      $$     开放集
├── 关系/事实的 validity_reasoning
├── fact_text 自然语言改写
└── 复杂时间推理、跨句因果推断
```

在这个架构中，**实体类型分类发生在 Layer 1（GLiNER），是封闭集操作**。而关系类型在 Layer 3（LLM）中保留了有限的开放性（"允许 LLM 自行生成 SCREAMING_SNAKE_CASE 格式的关系类型"）。

这意味着：实体类型必须是封闭集，关系类型可以是半开放集。两者的约束来源不同——前者受限于模型能力，后者受限于 prompt 设计。

### 4.5 GLiNER 对各 label 的预期效果差异

GLiNER 对 label 的语义理解依赖 label 文本本身在预训练语料中的分布。不同于 LLM 可以通过 system prompt 中的详细定义来理解领域特定标签，GLiNER 主要靠 label 词本身的语义。

| label | 预期效果 | 原因 |
|-------|---------|------|
| PERSON | ⭐⭐⭐⭐⭐ | 通用 NER 高频类型，训练数据中大量出现 |
| ORG | ⭐⭐⭐⭐⭐ | 通用 NER 高频类型 |
| RESOURCE | ⭐⭐⭐⭐ | 接近 NER 中的 "Product" / "Artifact" |
| TOOL | ⭐⭐⭐ | 领域特定，需要验证 zero-shot 效果 |
| CONCEPT | ⭐⭐ | 抽象概念类，GLiNER 可能倾向不标注或与 TOOL 混淆 |
| ACTION | ⭐⭐ | 与动词/事件触发词重叠，可能和 Prompt 2b 的事件检测混淆 |

这个预期需要在标注实验中验证。如果 CONCEPT 和 ACTION 的 F1 确实很低，这就是数据驱动的类型调整依据。

## 5. CONCEPT 与 RESOURCE 的边界处理

这是 review 中重点讨论的一个问题。两类在"概念被实例化"的场景下会产生边界模糊。

### 5.1 判断规则

我们采用**可定位性优先**的决策顺序：

1. 有具体的定位标识（文件路径、URL、数据库 ID）→ **RESOURCE**
2. 是某次交互的具体产出物 → **RESOURCE**
3. 是通用知识、方法、算法、参数名 → **CONCEPT**
4. 以上都不满足 → 通过上下文消歧

### 5.2 为什么这个边界模糊是可接受的

经过讨论，我们认为 CONCEPT/RESOURCE 的边界模糊**不构成设计缺陷**，原因是：

- 在有文件路径/URL 等定位标识时，区分是清晰的
- 在模糊案例（如"CSV"、"DataFrame"）中，即使分错类型，对检索结果的影响也很小——因为核心信息已经在 EventNode 和关系边中，EntityNode 的类型标签只影响检索时的 prompt 构造方式
- 容错空间足够大，不值得为此引入更复杂的机制

### 5.3 给 LLM 的判断提示

在实体抽取的 Prompt 中，我们补充了一条自问测试来帮助 LLM 在模糊案例中做判断：

> 问自己：这个实体消失了（文件被删/数据被清），相关的知识还有意义吗？
> - 没有意义（因为它就是那个东西本身）→ RESOURCE
> - 有意义（因为它是一种规律/概念/方法）→ CONCEPT

## 6. 优势总结

**1. 与下游检索直接对齐。** 类型决定了检索时的召回策略和 prompt 构造方式。类型即接口，从定义到使用一条直线，没有中间的转换损耗。

**2. 对判别式模型和 LLM 都友好。** 分类判断有行为锚点——无论是 GLiNER 的 zero-shot 标注还是 LLM 的 prompt 分类，都不需要做哲学判断，只需要问"这个实体会被怎么用"。6 个 labels 在 GLiNER 的最优性能区间内，同时也足够让 LLM 保持分类一致性。

**3. 适配 Agent 场景的信息密度。** Agent 运行时天然是工具驱动的，TOOL 和 RESOURCE 在 Agent 场景中出现频率最高，这套分类对这两类的区分最清晰。

**4. 有理论根基但不教条。** 语义角色理论提供了分类的理论合理性，但我们没有照搬——CONCEPT 和 ACTION 是根据 Agent 场景的实际需要补充的。理论指导方向，工程决定边界。

## 7. 待验证的风险

以下是 review 中识别出的需要用真实数据验证的风险点。

### 7.1 ACTION 与 EventNode 的职责重叠（最高风险）

"排查报错"既可以是一个 ACTION 类型的 EntityNode，也可以是一个 `event_type=user_request` 的 EventNode。同一个语义在图谱里可能被表示成两种结构。

**风险**：如果 ACTION 实体大量出现且与 EventNode 的 trigger 高度重复，会导致图谱冗余和检索时信息分散。

**验证方法**：在 20-30 条真实数据上统计 ACTION 实体的出现频率，以及它们与 EventNode trigger 的语义重叠度。如果重叠度 > 70%，考虑移除 ACTION 类型，将其职责完全交给 EventNode。

### 7.2 ORG 在 Agent 场景中的存在感

当前示例中 ORG 类实体（Acme Corp、DataPlatform）出现频率可能很低。如果实际数据中 ORG 占比 < 5%，维护这个类型在 prompt 中的指令（占用 prompt token）是否值得需要评估。

**验证方法**：统计真实数据中各类型的分布比例。如果 ORG 长期低频，可以合并到 CONCEPT（作为一种组织概念）或直接移除。

### 7.3 GLiNER 对领域特定 label 的分类能力

GLiNER 的 zero-shot 能力对通用 NER 类型（PERSON、ORG）效果好，但对领域特定类型（TOOL、CONCEPT、ACTION）的效果不确定。如果 CONCEPT 的 F1 < 0.6，可能需要：
- 更换 label 名称（如 CONCEPT → KNOWLEDGE 或 TERM）
- 对 GLiNER 做领域微调
- 将 CONCEPT 的分类降级到后处理规则层

**验证方法**：用标注数据集分别评估 6 个 label 的 Precision / Recall / F1，找出短板类型。

### 7.4 封闭集的类型覆盖度

GLiNER 只能从预定义的 6 个 labels 中选择。如果某个实体不属于任何一类，GLiNER 的行为是：要么强行归到最接近的类型（置信度低），要么直接不输出（漏抽）。

**风险**：持续出现某类实体无法归入 6 类，导致系统性漏抽。

**缓解措施**：
- 低置信度实体（score < 阈值）标记为待审核，定期分析其分布
- 如果某一类"无法归类"的实体持续高频出现，触发类型扩展评估
- 类型扩展需要评估对已有类型分类准确率的影响（加一个新 label 可能导致已有 label 的 F1 下降）

### 7.5 分类一致性

同一个实体在不同上下文中出现时，GLiNER 是否能给出一致的类型判断？比如 pandas 在所有 Block 中都被分为 TOOL，而不是偶尔被分为 CONCEPT。判别式模型的一致性通常比生成式 LLM 好（同样的输入必然得到同样的输出），但不同上下文中同一实体的 span 文本可能不同（"pandas" vs "pd" vs "那个库"），这仍然可能导致分类不一致。

**验证方法**：对同一批实体在不同 Block 上下文中重复抽取 3-5 次，统计类型一致率。目标 > 90%。

## 8. 最务实的改进建议

### 8.1 用真实数据标注验证

**在正式实现前，用 20-30 条真实 Agent 对话手工标注一遍。**

标注时记录每一个分类犹豫点，重点盯三类情况：

- 某实体犹豫超过 3 秒才确定类型 → 方法论边界，需要补充判断规则
- 某实体觉得"两个类型都说得通" → 需要在后处理规则中加消歧逻辑
- 某实体觉得"现有 6 类都不合适" → 可能需要调整类型体系

那些犹豫点的统计分布，才是决定类型体系是否需要调整的真正依据。**规则调整应该由数据驱动，而不是由讨论驱动。**

### 8.2 GLiNER 对比实验

用同一批标注数据，对比 GLiNER 和 LLM 在实体抽取上的效果：

| 指标 | 说明 | 目标 |
|------|------|------|
| 各 label 的 F1 | 哪些类型 GLiNER 做得好，哪些做不好 | F1 > 0.8 |
| 一致性率 | 同一实体在不同上下文中的类型一致率 | > 90% |
| 漏抽率 | GLiNER 完全没有标注的实体比例 | < 15% |
| 错分率 | 标注了但类型错误的比例 | < 10% |

如果某个 label 的 F1 持续低于 0.6，优先考虑：更换 label 名称 → 合并到相近类型 → 领域微调，按成本从低到高尝试。

### 8.3 类型扩展的触发条件

既然是封闭集，必须定义"什么时候打开这个集合"：

- 当连续 N 个 block 中出现高频实体但 GLiNER 置信度 < 0.3 → 可能需要新类型
- 新类型加入后需要在标注集上回归测试，评估对已有类型 F1 的影响
- 如果 GLiNER zero-shot 对新 label 效果不好，评估是否需要 fine-tune

当前方案已经足够启动验证，不应该在类型定义上继续空转。
