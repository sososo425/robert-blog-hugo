## 三、模块 D 归属：从 Group 3 剥离为公共层

你的直觉是对的：**模块 D 不应该放在 Group 3**。

### 问题分析

当前 Group 3 承担了 **Graph 构建** + **全部存储运维**，实际上是两个完全不同的技术域：

| 工作性质 | Graph 构建 | 存储运维 |
|---------|----------|--------|
| 技术域 | 知识图谱、NLP | 数据库、基础设施 |
| 节奏 | 研究→实验→迭代 | 部署→Schema→运维 |
| 消费方 | 自己 + Group 4 | **所有 Group** |
| 风险类型 | 算法不确定性 | 系统稳定性 |

把存储绑在 Group 3 导致两个问题：
1. Group 3 又要攻坚实体消歧等最难问题，又要管三套存储系统的 Schema/运维，精力被撕裂
2. Group 2 和 Group 4 写入/读取存储时，要跟 Group 3 对接——本质上 Group 3 变成了所有人的瓶颈

### 建议方案：Storage Abstraction Layer 由 TL 统筹为公共层

新架构图已经画出了 **Storage Abstraction Layer**，利用这个架构变化，做如下调整：

```
模块 D（Storage Abstraction Layer）= 公共层
├── Schema 设计：各 Group 在 TL 协调下共同定义
│   ├── Tree 相关 Collection（ams_blocks / ams_sections）→ Group 2 提需求
│   ├── Graph 相关 Collection + Neo4j Schema          → Group 3 提需求
│   └── 检索相关索引优化                               → Group 4 提需求
├── SDK 封装：TL 主导，Phase 1 第一周完成基础版
│   └── 统一 write() / read() / search() 接口
├── 部署 & 运维：拆分给各组就近负责
│   ├── Milvus → Group 2（Tree 是最大用户）
│   ├── Neo4j → Group 3（Graph 独占）
│   └── LanceDB → Group 1（多模态原始数据）
└── 跨存储一致性 & Memory Lake 预研 → TL
```

### 对 Group 3 的影响

Group 3 的工作清单从 10 项精简到 7 项，去掉的是：

| 移出的工作项 | 新归属 |
|------------|-------|
| Milvus/LanceDB Schema 与运维 | Group 2（Milvus）/ Group 1（LanceDB） |
| 跨存储 ID 映射与一致性保证 | TL 公共层 |
| Memory Lake 预研 | TL 公共层 |

Group 3 可以专注于：**实体消歧 → 社区发现 → Temporal KG → 遗忘机制 + Neo4j 运维**。难度仍然是最高的，但至少不再被存储运维分心。
