## 纵向 vs 横向分工：本质差异

```
当前方案（纵向 / by structure）：
  Group 1: ETL Pipeline         ← 所有数据源都经过这里
  Group 2: Tree 构建             ← 所有内容类型都用这套
  Group 3: Graph 构建 + 存储     ← 所有内容类型都用这套
  Group 4: 检索服务

替代方案（横向 / by content type）：
  Team A: Agent-TES 数据         ETL → Tree → Graph → 存储 → 检索
  Team B: 知识文档（PDF/MD）      ETL → Tree → Graph → 存储 → 检索
  Team C: 代码（Python/Java）     ETL → Tree → Graph → 存储 → 检索
  Team D: 技能文件（skill.md）    ETL → Tree → Graph → 存储 → 检索
```

---

## 纵向（当前方案）的考量逻辑

**为什么按 Tree / Graph 来分？**

核心逻辑是：**Tree 和 Graph 是两套截然不同的技术域**，不是同一能力的重复。

| 维度 | Tree 构建 | Graph 构建 |
|------|-----------|-----------|
| 核心算法 | 层次聚类、标题解析、摘要聚合 | NER、实体链接、消歧、社区发现 |
| 技术依赖 | LLM 摘要、Chunking | 知识图谱理论、Louvain/Leiden |
| 数据流 | Block → Section → Root | Triples → Node → Community |
| 人才需求 | 文档理解 + 结构算法 | 图论 + 实体识别 |

而且，**Raw Block 是两者共同消费的标准接口**，Group 1 生产一次，Group 2/3 并行消费，这是一种干净的流水线分工。

---

## 如果按横向（内容类型）划分，会有什么问题？

### ❌ 主要问题

**1. 核心算法大量重复**

Tree 构建逻辑（自动分层 + 摘要聚合 + 增量更新）每个 Team 都要实现一遍。
Graph 构建逻辑（NER + 实体链接 + 消歧 + 社区发现）也要重复四次。

这不只是代码重复，是**高难度算法的重复研究**，成本极高。

**2. 结构一致性极难保证**

四个 Team 分别构建 Tree 和 Graph，写入同一个 Neo4j 和 Milvus，会出现：
- 实体 `"Python"` 在文档 Team 和代码 Team 里被建成两个不同节点，图谱裂开
- Tree 的 Block Schema 字段定义不同，检索时 Group 4 无法统一处理
- Graph 的边类型定义漂移，社区发现跨类型失效

**3. 每个 Team 都需要全栈能力**

横向 Team 要懂：PDF 解析 + AST 解析 + LLM 摘要 + 图谱构建 + 存储运维 + 检索。
以 2 人一组的规模，**没有任何一组能做好**。

**4. 检索层无法复用**

检索服务（BM25 + 向量 + Tree 导航 + Graph PPR）是针对统一结构设计的。如果每个内容类型的结构不同，检索就要针对每种内容重新实现一套逻辑。

---

### ✅ 横向划分的合理优势（也要承认）

| 优势 | 说明 |
|------|------|
| **端到端自治** | 一个 Team 对某类数据的全链路负责，出问题不需要跨组协调 |
| **内容特化优化** | 代码的 Tree 可以是 AST 树（函数/类/模块），而不是标题层级；文档是另一套 |
| **按内容类型迭代** | 可以先上文档，再上代码，横向 Team 各自推进互不阻塞 |
| **故障隔离** | 代码 Pipeline 挂了不影响文档检索 |

## 两种方案的本质取舍

```
纵向（当前）= 技术分层，算法专精，结构统一
横向（替代）= 业务分域，端到端自治，来源特化
```

| 维度 | 纵向（当前） | 横向（按内容类型） |
|------|------------|-----------------|
| 代码复用 | ✅ 高 | ❌ 大量重复 |
| 知识图谱一致性 | ✅ 天然统一 | ❌ 需要额外协调层 |
| 端到端自治 | ❌ 跨组依赖明显 | ✅ 每组独立 |
| 内容特化优化 | ❌ 需跨组协调 | ✅ 自然 |
| 人力要求 | ✅ 各组专精 | ❌ 各组全栈 |
| 按内容类型增量交付 | ⚠️ 较难 | ✅ 自然 |
| 适合团队规模 | ✅ 小团队（8-9人） | ❌ 需要更大规模 |

## 真正的折中：混合方案

实践上，你们架构图中的 **online/offline pipeline 分法**其实已经是一种"半横向"：

```
Online Pipeline  → 主要处理 Agent-TES 实时行为数据
Offline Pipeline → 主要处理文档、代码、技能文件
```

这个分法按**数据流特征**（实时 vs 批量）而非纯结构来切，但 Tree/Graph 构建逻辑仍然共享。

如果想在当前基础上引入内容特化，更合理的方式是：

```
Group 2（Tree）内部再细分 parser 策略：
  - 文档 Tree：标题层级解析
  - 代码 Tree：AST-based 解析（完全不同）
  - 对话 Tree：时序分段

但 Tree 数据结构、摘要逻辑、索引写入仍共用一套
```

即：**接口统一，实现内部针对内容类型做 strategy pattern 分叉**。这样既保留纵向的一致性，又在需要时引入横向的特化能力。

---

## 结论

> 当前纵向分法是正确的**架构选择**，适合这个团队规模和技术目标。横向分法的核心价值（端到端自治、内容特化）可以通过**在模块内部做 strategy 分叉**来实现，不需要打破整个分工结构。
> 
> 唯一需要警惕的是：代码数据的 Tree 构建（AST-based）和文档 Tree（标题层级）差异足够大，Group 2 要提前设计好 parser 插件化机制，否则后期代码支持会比较痛。
