# Tree + Graph 存储结构整体原理

> **版本归属**: 版本C
> **文档定位**: 核心架构原理说明补充资料
> **关联章节**: 《00-概要设计》第 3 章（记忆分类体系）与第 5 章（内部结构）

在 Agent Memory System (AMS) 中，长期记忆的存储采用了 **Tree（树状结构）** 与 **Graph（图结构）** 结合的双轨或单轨模式。这不仅仅是数据库选型（Neo4j vs Redis/Milvus）的结果，更是基于**认知科学隐喻**、**数据内在形态**以及**未来检索模式**的全局架构考量。

本文将从第一性原理出发，系统性阐述 Tree 和 Graph 在 AMS 中的本质区别，以及不同数据源为何必须遵循特定的映射约束（`Graph ONLY`、`Tree ONLY`、`Tree + Graph`）。

---

## 1. 核心认知与检索哲学

AMS 的核心设计哲学是：“**搜索才是记忆的核心，记忆的构建是为了支持有效的搜索。**”

如果存储的数据无法在极短的延迟（p95 < 200ms）内被精准、关联地召回，那记忆就失去了意义。因此，结构的选型完全取决于 Agent 思考和调取知识时的“思维方式”。

### 1.1 Tree 结构：层级抽象与归纳（Hierarchical Abstraction）

**底层逻辑**：自底向上抽象，自顶向下导航。
**认知隐喻**：人类在阅读一本书时，先看目录（大纲），再看章节摘要，最后寻找具体段落。
**解决的核心问题**：“大局观”与“全局主题提取”。

*   **构建方式**：从最基础的叶子节点（Block: raw text, code snippet, image）向上聚合成更宽泛的主题摘要（Section L1 -> Section L2 -> Document）。
*   **检索价值**：当 Agent 被问及“这篇文档/这个仓库的主旨是什么？”时，无需暴力遍历所有细节块，直接通过向量检索命中高层的 Section/Document 聚类节点即可。它擅长处理**静态的、有强内聚结构的知识**。

### 1.2 Graph 结构：关联拓扑与时序（Relational & Temporal Topology）

**底层逻辑**：节点代表实体/动作，边代表语义/时序/因果关系。
**认知隐喻**：人类的联想式回忆（“顺藤摸瓜”）。提到 A，想起了 B，因为 A 和 B 昨天同时出现过。
**解决的核心问题**：“多跳推理（Multi-hop Reasoning）”与“因果/时序回溯”。

*   **构建方式**：从 Block 中抽取核心词（Phrase Node），并通过实体关系（Relation Edge）、上下文回指（Context Edge）和时间线（Temporal Edge）形成一张巨大的网。
*   **检索价值**：当 Agent 必须跨越不同的文档、跨越不同的对话会话，去寻找隐晦的关联时（例如：“上次解决这个 Bug 时调用的那个 API 是什么？”），Graph 允许系统沿着边进行游走，实现逻辑推理的补全。

## 2. 存储结构约束策略（数据源映射规则的根本原因）

在 AMS 的摄入管道中，强制执行了严格的数据源映射规则。以下是不同数据源被迫采用 `Graph ONLY`、`Tree ONLY` 或 `Hybrid` 的底层原因。

### 2.1 为什么 User-Agent Interaction 和 Execution Traces 是 Graph ONLY？

这两类数据代表了 Agent 的**动态行为流**，对应 Declarative Memory 中的 Episodic Memory（情景记忆）和 Procedural Memory（技能经验）。

**强制使用 Graph ONLY 的原因**：

1.  **缺乏静态层级结构（No Intrinsic Hierarchy）**
    人机对话或工具执行链，是一条随着时间流逝不断延伸的**线性状态流**。强行把前 10 轮对话或者前 5 次 API 调用聚合成一个“Section L1”，在认知和业务上都是极其生硬的。动态的数据流不适合静态的树。
2.  **核心价值在于“时序状态”与“关联发散”**
    交互与追踪数据的核心是：“**当时发生了什么，以及为什么发生？**”
    *   **时序性（Temporal Dependency）**：“步骤 A 失败” $\xrightarrow{导致}$ “尝试步骤 B”。这种带有因果链的时间戳序列，只能用图中的时序边（Temporal Edge: `[:FOLLOWS]`, `[:CAUSED_BY]`）来完美表达。
    *   **跨越时空的实体关联**：用户今天提到的问题可能与三周前的某个意图有关。通过 Graph 中的短语节点（Phrase Node），可以将孤立的时间线交织成语义网。
3.  **符合联想式回忆的提取模式**
    Agent 检索历史会话或历史执行轨迹时，依靠的是“线索式遍历”，而不是“翻阅目录”，因此完全不需要构建 Tree 的多级摘要。

### 2.2 为什么 Skill Markdowns 是 Tree ONLY？

这类数据对应 Agent 提炼出的标准化、结构化动作配方（Procedural Memory 的硬编码抽象形式）。

**强制使用 Tree ONLY 的原因**：

1.  **纯粹的层级目标分解**
    一个可执行的技能（Skill），其内在逻辑天然是**自顶向下分解**的：
    `Root (大目标) -> H1 (子任务) -> H2 (具体步骤) -> Leaf (参数与工具)`。
    这完全吻合树状结构的语义。
2.  **防偏离执行的刚性需求**
    执行技能时，Agent 需要像照着说明书操作一样严谨。Graph 的网状结构容易导致思维的发散与跳跃，而 Tree 则能提供线性的深度优先或广度优先执行指引。强制剔除 Graph 边，是为了在执行阶段“降低信噪比”，保证动作的精准性。

### 2.3 为什么 Work Documents / Source Code 是 Tree + Graph (Hybrid)？

工作文档与源码库，是信息密度最高、结构最复杂的静态物料（Declarative Memory 中的 Semantic 子类）。

**必须双轨并行的原因**：

1.  **既需要“目录大纲”，又需要“网状交叉引用”**
    *   一份业务文档有严密的章节逻辑，一个代码库有“目录-文件-类-方法”的包裹关系，这是典型的 **Tree 结构**。
    *   但是，文件 A 中的函数可能调用了文件 B 中的接口（Call Graph），文档甲中的某个术语（Entity）正是文档乙的探讨主题（Knowledge Graph）。这种错综复杂的网状依赖，是 Tree 无法描述的，必须依赖 **Graph**。
2.  **Context Edge（双向桥接）的关键作用**
    如 AMS 架构图所示，**Tree 层级的底层（Block）与 Graph 层级的实体（Phrase Node）通过 Context Edge 紧密相连**。
    这种 Hybrid 模式使得 Agent 具备了极其强大的检索能力：
    它可以先在向量库中找到相关的实体节点（Graph），然后通过 Context Edge 瞬间“跳回”该实体所在的源码文件（Tree的叶子节点），接着顺着 Tree 向上查找，获取该文件整体的 Summary（大局观）。

## 3. 总结

在构建 Agent Memory System 时，结构绝非随意的技术堆砌：

*   **Tree ONLY** 适用于**行动指令（Skill）**，追求执行的严谨和目标的层级拆解。
*   **Graph ONLY** 适用于**时间流/事件流（Interaction/Trace）**，追求因果链路的追溯和跨时空的语义联想。
*   **Tree + Graph** 适用于**高密度静态语料（Docs/Code）**，追求宏观归纳与微观依赖兼备的多维知识图谱。

这种基于数据特性的精细化处理，是 AMS 区别于传统单一形态 RAG（单纯向量切块或单纯建立知识图谱）的核心认知优势。
