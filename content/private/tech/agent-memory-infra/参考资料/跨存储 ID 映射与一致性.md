---

## 通俗解释

### 1. 问题背景

AMS 采用了**多存储引擎架构**：
- **Milvus**：存储向量（Block/Section/Node 的 embedding）
- **Neo4j**：存储知识图谱（实体关系、社区结构）
- **LanceDB**：存储多模态原始数据（文本、图片、视频）

**同一个逻辑对象**（比如一个文档段落）会同时存在于这三个存储中，但每个引擎有自己的内部 ID 体系。

### 2. 具体例子

以一个 **文档 Block**（比如一段讲"Kafka 消息队列架构"的文本）为例：

| 存储引擎 | 存储内容 | 该存储中的 ID |
|---------|---------|--------------|
| **Milvus** (`ams_blocks`) | `block_id="blk_001"`, embedding 向量, summary | Milvus 内部 auto-id |
| **Neo4j** | 从 Block 提取的三元组：`(:PhraseNode {name:"Kafka"}) -[:RELATION]-> (:PhraseNode {name:"消息队列"})` | Neo4j 内部 element-id |
| **LanceDB** | Block 的原始多模态数据（原文 + 附图） | LanceDB 行 ID |

**如果没有统一 ID 映射：**
- 向量检索在 Milvus 找到了 `blk_001`
- 图检索在 Neo4j 找到了 `node_kafka`
- 系统**无法知道这两者有关联** → 检索结果变成"孤岛"，无法融合

### 3. 两个核心层面

| 层面 | 含义 |
|-----|------|
| **ID 映射** | 设计全局统一的 ID 体系（如 `block_id`, `section_id`, `node_id`, `doc_id`），让同一个逻辑对象在三个存储中可以互相找到 |
| **一致性** | 保证对同一对象的增删改操作在多个存储中要么全部成功，要么有补偿机制，不出现"半更新"的脏状态 |

### 4. 实际应用场景

#### 场景一：多路检索融合（模块 E）
```
1. Graph 检索在 Neo4j 找到 "Kafka" 实体（PPR 高分）
2. 向量检索在 Milvus 找到 blk_001（余弦相似度高）
3. 通过统一 block_id 关联，确认两者来自同一文档 → 融合排序
```

#### 场景二：Tree 增量更新（模块 B）
```
1. 文档更新 → Group 2 更新 Milvus 中的 ams_blocks
2. 同时需要标记 Neo4j 中对应三元组为"过时"
3. 需要 LanceDB 同步更新原始数据
→ 通过统一 doc_id/block_id 作为"桥梁"实现联动
```

## 为什么这是 P1 优先级？

在大纲中明确标注：

> **TL 主导、P1 优先级**——它是跨所有 Group 的公共问题，设计不好后面会到处踩坑。

因为：
1. **Group 2（Tree）** 向 Milvus 写入 Block 向量
2. **Group 3（Graph）** 从 Block 提取三元组写入 Neo4j
3. **Group 1（ETL）** 管理 LanceDB 原始数据
4. **Group 4（检索）** 需要做多路融合

**所有 Group 都需要遵循同一套 ID 规范**，否则无法协作。

---

## 总结

"跨存储 ID 映射与一致性"就是解决：**如何在多个异构存储之间，用统一的"身份证"识别同一个对象，并保证数据变更时的同步性**。这是 AMS 架构的**基础设施层问题**，需要在 Phase 1 就打好基础，否则后续的检索融合、增量更新都会出问题。
